# Moving board data into SQLite (minimal plan)

Status: **2026-10-26 the user confirmed the minimal plan; in implementation**. Card "Data storage and loading optimization". This file replaces the full design of 2026-10-25, the subtraction draft (D1–D4) and the migration test plan; the old text, the 18 fixture increments and all evidence are kept as is in the local branch `archive/sqlite-r1-v1` (not pushed).

## 1. Decisions

The user's instruction on 2026-10-26: finish the SQLite migration first, then do the loading optimization; simplify as much as possible while it stays rollback-able and loses no data, and avoid over-design. Accordingly:

| Old decision | Now |
|---|---|
| D1 The user must confirm before the first migration | Migrate automatically at startup. Before migrating, the whole original file is saved into a snapshot; on failure it keeps using JSON and use is not affected. |
| D2 After a restore the send queue is persistently paused for manual checking | No longer needed: the send queue (composer) stays in JSON, restoring a backup does not touch it, and nothing is resent. |
| D3 Anomaly originals kept one by one, browsable | Narrowed to keeping the whole source snapshot: the migration accepts only boards the existing reader can read; if it cannot read it, it does not migrate. |
| D4 Rollback only to a specified JSON package with request-generation checks | Changed to "export as a v5 board.json + add an offset to all revisions", after which the previous public version can be installed straight back. Signed requests and RPC shapes are both unchanged, so the old version can read directly and old requests are rejected because of a revision mismatch. |

Not done (removed from the old plan): a specified rollback package, storageEpoch/generation, `storage.mutate-v1`, the 11-phase control/journal state machine, the reimport flow, a strict JSON parser, a raw-text table, putting side files into the database, a two-phase send ticket, a filesystem allowlist and platform matrix, 10 maintenance RPCs.

## 2. Scope

- Only `board.json` moves into SQLite: projects, tasks, events, ideas, links, artifacts, workpads, plans, attentionDismissals, agentReceipts and revision.
- Unchanged: summaries, memory, digests, workflow insights, outside sessions, composer (drafts/queue/images), the various read watermarks, flow/commands logs, and `.flowly/project.json` in the project folder. They are still atomic JSON files of their own.
- Read behavior is unchanged: all RPCs still get the same Board. Loading optimization (on-demand reads, partial refresh) is the next step, done separately after this plan is stable, reusing the same database.

## 3. Files

All under `dataDirectory()`:

| File | Role |
|---|---|
| `flowly.sqlite` (and `-wal`/`-shm`) | Board data. The only business source. |
| `storage-owner.sqlite` | Process lock: only the Flowly process holding it may open the business database. It stores no data and takes no part in backups. |
| `board.json` | After migration replaced by a **retirement marker**: `{"version":0,"storage":"sqlite",...}`. An old version that reads it reports "data invalid" and refuses to write, and does not treat it as an empty board. |
| `migrations/<time>/` | The source snapshot before migration: the original `board.json`, `board.json.bak` and `manifest.json` (sha256, size). Kept permanently, not rotated. |
| `backups/flowly-<time>.sqlite` | Automatic and manual backups; only the latest 7 generated by this plugin are kept. |
| `flowly.sqlite.before-restore-<time>` | The current database before restoring from a backup, kept and not deleted. When a name collides within the same second a sequence number is added, and an existing file is not overwritten (the same below). |
| `flowly.sqlite.retired-<time>` | The database retired after exporting back to JSON, kept and not deleted. |
| `storage-mode.json` | Exists only after exporting back to JSON: `{"backend":"json"}`, meaning do not migrate automatically again. |

## 4. Table structure

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT;
-- schema = 1, one row for each of the board's scalar fields (version, revision), the value being JSON
CREATE TABLE items (
  collection TEXT NOT NULL,   -- the Board's array field name, e.g. tasks, events
  key TEXT NOT NULL,          -- id / key / taskId; add #sequence when duplicated within a collection
  ord INTEGER NOT NULL,       -- order within the array
  task_id TEXT,               -- to ease reading by card later
  project_id TEXT,
  body TEXT NOT NULL,         -- the JSON of this element
  PRIMARY KEY (collection, key)
) STRICT;
CREATE INDEX items_task ON items (collection, task_id);
CREATE INDEX items_project ON items (collection, project_id);
```

Collections are handled automatically from the Board's own array fields, so adding an array field to the Board later does not need a table change. Order is kept as is: when only appending/deleting, the `ord` of existing rows does not move, otherwise the whole group is renumbered.

The connection sets and reads back to confirm: `journal_mode=WAL`, `synchronous=FULL`, `busy_timeout`. Directory 0700; database, migration snapshot and backup files 0600.

2026-10-26 the user decided to accept the small risk of a sudden power loss on macOS, and not turn on `fullfsync` and `checkpoint_fullfsync`. macOS's fsync does not guarantee a write goes below the disk cache; in WAL mode the database can be damaged only if power is lost at the moment of a checkpoint, and normally a power loss loses at most the last few seconds of changes. The fallback is the daily backup.

## 5. Reads and writes

`BoardStore`'s business logic changes not one line; only "read the whole board / write the whole board back" is replaced by a persistence layer interface:

- **Read**: at startup read the whole board from the database, validate it with `storageSchema` and the existing invariants, and cache it in memory. `read()`/`view()` return a copy of the cache. Only this process writes the database (guaranteed by the owner lock), so the cache cannot go stale.
- **Write**: run the original operation on a copy → `revision+1` → the existing invariant checks → `storageSchema.parse` → compare element by element with the cache → in one `BEGIN IMMEDIATE` transaction write only the changed rows and the revision → update the cache only after the commit succeeds. Any step failing rolls back, the cache is unchanged, and the error is reported as today. Receipts (agentReceipts) are in the same transaction as the business data.
- `board.json` is no longer rewritten whole, and `.bak` is no longer copied. The flow log and `onCommit` (project folder export) still run after the commit.

## 6. Startup and first migration

When the plugin starts, all board reads and writes first wait for storage to be ready (the internal queue of `BoardStore`), with no extra gate needed. The rules are judged in order:

1. `storage-mode.json` is json: if `board.json` is already a real board → use JSON (after an export; if the database is still there, finish the rename, a rename failure is only logged and the database is left unused); if `board.json` is still a retirement marker → the export did not complete, delete `storage-mode.json` and continue with SQLite by the rules below.
2. The current Paseo has no `node:sqlite`, or the SQLite version is lower than 3.51.3 (3.50.x needs ≥3.50.7, 3.44.x needs ≥3.44.6; earlier versions have a WAL corruption defect) → use JSON. If the data is actually already in SQLite (board.json is a retirement marker), report an error saying Paseo must be upgraded, and never treat it as an empty board.
3. Take the owner lock. If it is occupied (usually the old process has not exited yet on reload), retry briefly; if it still fails report `STORAGE_BUSY` and try again at the next read or write. It does not fall back to JSON.
4. Delete a leftover `flowly.sqlite.tmp` (a half-finished uncommitted migration).
5. `flowly.sqlite` exists:
   - `board.json` is a retirement marker or does not exist → use normally (if it does not exist, write the marker).
   - `board.json` is a real board and its sha256 equals the original file in the latest migration snapshot → the last migration was interrupted "after the rename, before writing the marker"; write the marker and use normally.
   - Otherwise → `STORAGE_DIVERGED`: both copies are kept, nothing is chosen automatically, and the error message states the locations of the two files.
6. `flowly.sqlite` does not exist:
   - `board.json` is a real board → **migrate** (below).
   - `board.json` is a retirement marker, or `backups/` or `migrations/` exists → `STORAGE_MISSING`: no empty database is created; the storage page can still restore from a backup.
   - Nothing at all → a new install: create an empty database and write the retirement marker.

**Migration** (if any step fails: delete tmp, leave `board.json` untouched, keep using JSON this time and show the reason on the storage page; retry at the next startup):

1. Read `board.json` with the existing reader (including the v1–v4 upgrade). If it cannot be read, report "data invalid" as today, and do not migrate.
2. Copy `board.json` and `board.json.bak` into `migrations/<time>/`, write `manifest.json`, and read back to check sha256.
3. Create the tables in `flowly.sqlite.tmp`, write all rows in one transaction, `PRAGMA integrity_check`.
4. Re-read the whole board from the tmp database and compare value by value with the step 1 result (also through `storageSchema`); if they differ, fail.
5. checkpoint, close, fsync, `rename` to `flowly.sqlite` (the only commit point), fsync the directory.
6. Replace `board.json` with the retirement marker using tmp + rename.
7. Open the real database, then immediately make the first backup.

## 7. Backup and restore

- **Automatic backup**: one immediately after migration; after that, at each commit, if the last one is more than 24 hours old, make another in the write queue. Write to `.tmp` with `VACUUM INTO`, and rename after `quick_check` passes. When there are more than 7, delete the oldest (only files of the plugin-generated form `flowly-*.sqlite` are deleted). A failure is only logged and does not affect business writes.
- **Immediate backup**: the storage page button, same as above.
- **Restore**: choose a backup → validate first (`quick_check`, can be read and passes the schema and invariants) → in the write queue close the current database and rename it to `flowly.sqlite.before-restore-<time>` → copy the backup as tmp → add an offset to the revision of the board, all projects, tasks and workpads (the largest revision in the current database + 1) → rename to `flowly.sqlite` → reopen. The offset is added so that old edits and old agent requests sent before the restore are all rejected because of a revision mismatch, and the client also treats the restored board as newer data. It can also restore when the database is missing (`STORAGE_MISSING`).
- Restore does not change the send queue or other JSON files; the flow log may hold history events after the backup point, which affects only statistics, not the board.

## 8. Rolling back to JSON

The storage page "Export as JSON":

1. In the write queue read the current board and add an offset to all revisions (as above).
2. First write `storage-mode.json`, then write the board as a v5-format `board.json` (tmp + rename, replacing the retirement marker). If interrupted between the two steps, the next startup sees the retirement marker and treats the export as not having happened (§6 rule 1); if interrupted after board.json is written, the next startup completes the export.
3. Rename `flowly.sqlite` to `flowly.sqlite.retired-<time>`. A rename failure does not affect the export: board.json is already the board, and the database is left unused.
4. This process immediately switches to JSON and keeps working. The user can afterwards install the previous public version (it can read this board.json directly), or stay on the new version using JSON.

The storage page "Switch back to SQLite": first rename the leftover database, then delete `storage-mode.json` and immediately migrate per §6 (the same as the first migration, with the source being the current board.json).

After an export, in the rare case that a few card-creation requests that de-duplicate by operationId and carry no revision are replayed by an old context within the 15-minute validity period, at most one extra card appears, and no data is overwritten.

## 9. Storage settings page

Settings → Storage, which can be opened even when the board cannot be read:

- Status: the current backend (SQLite / JSON), the data directory, the database size, the migration time, the latest backup time; for JSON the reason is stated (not migrated, unsupported, the reason a migration failed, exported). The error states (BUSY / DIVERGED / MISSING) show the reason and the file locations.
- Buttons: Back up now; Restore from backup (lists backups, executes after confirmation); Export as JSON (executes after confirmation); Switch back to SQLite (JSON mode only).

RPCs: `storage.status`, `storage.backup`, `storage.restore`, `storage.export-json`, `storage.use-sqlite`. All are ordinary request-response, with no polling of progress.

## 10. Errors

| Code | When | What the user sees |
|---|---|---|
| `STORE_INVALID` | Same as today: board.json cannot be read | The original error |
| `STORAGE_BUSY` | The owner lock is held by another Flowly process | Retry later or reload the plugin |
| `STORAGE_DIVERGED` | The database and a real board.json both exist and are not the same copy | The two file locations, a manual choice is needed |
| `STORAGE_MISSING` | There are traces of SQLite but the database is not there | Restore from a backup |
| `STORAGE_UNSUPPORTED` | The data is in SQLite but the current Paseo cannot open it | Upgrade Paseo |

Logs write only file names, sizes, row counts and durations, and not board content.

## 11. Acceptance

**Implementer self-test** (before delivery, in a temporary worktree of the commit): `npm run typecheck`, `npm test`, and the following focused tests:

1. After migrating v1–v5 samples, the result is value-for-value the same as what the old reader reads; an empty `tags: []` and a missing `tags` stay distinct; duplicate event ids keep every one and the order.
2. The same series of business operations (create project, create card, edit, events, receipts, ideas, artifact, workpad, delete card, remove project) is run on the JSON and the SQLite persistence layers separately, and after each step the whole board is the same on both sides; still the same after reopening the database.
3. A failure midway through a write: the database and the cache are both unchanged, and the next write is normal.
4. A failure at every step of the migration leaves the original board.json unchanged and keeps using JSON; the next startup can migrate again.
5. Startup rules: a leftover tmp is deleted; an interruption after the rename and before writing the marker can be completed; DIVERGED and MISSING do not create an empty database; a new install creates an empty database and writes the marker; without `node:sqlite` or with a version that is too low, JSON is used.
6. When a second process cannot get the owner lock it reports BUSY and does not fall back to JSON.
7. Backup → modify → restore: the board returns to the backup content, all revisions get larger, edits with an old revision are rejected, the database from before the restore is kept; when there are more than 7 only the oldest own backup is deleted.
8. Export as JSON: the board read by the old reader (the JSON persistence layer of `BoardStore`) is the same as before the export (except revision), an edit with an old revision is rejected; the database is renamed and kept; after switching back to SQLite the data is consistent. When the export is interrupted between the two file writes, or the database cannot be renamed, the state is consistent after restart.
9. Kill the child process at two places in the migration, "before the rename" and "after the rename, before writing the marker", and after restart both converge to a complete old state or a complete new state.
