# Dispatcher (DISPATCHER-SPEC)

One Flowly-owned agent session per board group (BOARD-GROUPS-SPEC, ruling Noah 2026-11-10): it hears the stops of its group's cards, creates and starts cards in any live project of its group, parks asks as project ideas, and, when the user asks and confirms, creates projects and manages groups. "The dispatcher" below is the dispatcher of one group (`groupId`), and "all projects" means that group's live member projects. Contract only; progress is in `docs/PROGRESS.md`. This document covers the agent, its workspace, its credential and tools, and note delivery. The chat panel (Task 10) and asks in the chat (Task 11) extend it.

Status: user decisions 2026-11-08 (single-pane spec D1, D2; plan Decisions Q5, Q6; one long-lived dispatcher session). AGENTS.md records the dated user-requested exception (role orchestration and automatic session starts by a plugin-owned background session whose workspace is never archived; a dead dispatcher (archived or missing) is replaced, a stopped (closed) one is resumed, and Flowly archives a dispatcher session only on the user's confirmed Replace dispatcher of an unguarded one).

## 1. Stored record

`<dataDir>/dispatcher.json`:

```json
{ "version": 2, "workspaceId": "…" | null, "groups": { "<groupId>": { "agentId": "…", "workspaceId"?: "…", "startedAt": "ISO time", "seenRevision"?: number, "seenIds"?: string[], "previousAgentIds"?: string[], "savedTools"?: true | string[], "guard"?: { "version": number, "provider": "…" } } }, "previousAgentIds"?: string[], "unassigned"?: { …an entry }, "legacyGroupId"?: "<groupId>" }
```

One entry per group that has a session; a group without an entry reads as `none`. The top-level `workspaceId` is where new sessions start; an entry's `workspaceId` is the workspace its own session was started in (a migrated v1 entry takes the v1 value; an entry without one falls back to the top-level value), and the caller check (§4), the tail and the open hook use the entry's, so another group's start in a new workspace never locks a live session out. The workspace of any entry counts as the dispatcher's (§2: never bound to a card, never archived). `seenRevision` and `seenIds` are the user's "Changed since you looked" mark (§9.2) for that group; the entry's `previousAgentIds` are that group's earlier dispatcher sessions, oldest first, at most 20 while the group exists. The top-level `previousAgentIds` is the global list of dispatcher session ids of this install that no group entry holds any more (overflow beyond 20, ids of replaced sessions' groups that were deleted), capped at 100; the change line (§9.2) and the batcher's `exclude` (§7) read every id ever recorded (current ids, entries' previous ids and the global list), so a past dispatcher's events never show up as news. `unassigned` holds a migrated v1 session while no group exists yet (below) and `legacyGroupId` names the group the v1 session moved to, which unstamped v1 chat notes belong to (§9.1). `savedTools` lists the tools a session was created with, saved and preapproved (§3; the confirmed tools of §5.2 are never in it); `true`, written by the first such sessions, stands for the first eight tools (§5, from `flowly_list_projects` to `flowly_link_cards`); absent when the open hook adds the server. `guard` is what the session was started without (§3): `dispatcherGuardVersion` and the provider part of its model; absent for a dispatcher started before it. A start Paseo refuses restores the earlier record's value. Every write keeps the fields it does not change.

- Written atomically (temporary file + rename, mode 0600) and serialized; a missing file is the empty record (all `null`).
- A file that does not parse or validate is renamed to `dispatcher.json.invalid-<epoch ms>` (kept, never deleted) and treated as empty; the next write creates a fresh file.
- The record names each group's one current dispatcher. A new dispatcher starts only when that group's stored one is dead (§3); it replaces the entry's `agentId` and `startedAt`, and the dead session's id moves to the end of the entry's `previousAgentIds`. The dead session loses its tools (§4).
- Migration (BOARD-GROUPS-SPEC §7 step 4), idempotent and independent of projects: a v1 file (`version: 1`, one session) becomes v2 once the board has groups. Its session moves to the group with the most open cards (not archived, not Done or Cancelled, on a live project; ties: the first group in order, also on a board of groups with no projects), keeping `agentId`, `startedAt`, seen mark, `previousAgentIds`, `savedTools` and `guard`; the workspace is unchanged and `legacyGroupId` is set. With no group yet, the file is written as v2 with the session in `unassigned` and moves when a group exists (it gets no open-hook credential until then). Run at plugin start after the board's group migration, after a storage restore and lazily by the lifecycle calls; the board is written first, then the record, and a crash between them is repaired by the next run. A file of another version, or that does not validate, is preserved as invalid (above), never overwritten. A deleted group's entry is removed with the group, after its session was archived (§3).

## 2. Workspace

- One workspace and folder serve every group's dispatcher: each group's session is a session in it, titled `Flowly dispatcher · <group name>` (the title is not updated on a group rename; it follows at the next start or replace), labelled `flowly-dispatcher=1` and `flowly-dispatcher-group=<groupId>`.
- A directory workspace on the **dispatcher folder** `<Paseo home>/flowly-dispatcher/dispatcher` (the Paseo home is `PASEO_HOME`, else `~/.paseo`, the same home the plugin data folder is derived from), titled "Flowly dispatcher", created with `background: true` and without a Paseo project id, so Paseo files it under its own project for that directory, apart from every Flowly project. The folder and its parent are created with mode 0700, and set to 0700 at every start when they already exist.
- Why there (ruling, Noah 2026-11-09): the dispatcher's working folder (its cwd) keeps the plugin data out. Inside the plugin data folder, a provider that auto-allows reads or edits inside the cwd covered `board.json`, `flowly.sqlite`, the token-sealing key and plugin settings; now such access goes through the provider's permission prompts. A direct child of the Paseo home would put Paseo's own credentials and configuration next to it; its own parent, `flowly-dispatcher`, holds the dispatcher folder only. This is not a sandbox: in a full-access or bypass mode, or by absolute paths, the agent can still reach any file the user can (`../..` from the folder is the Paseo home). The real boundary is the sealed dispatcher credential (§4) plus the provider's permission prompts. The host offers plugins no other per-plugin working folder. The folder keeps the name `dispatcher`, so Paseo's project for it keeps its name.
- At every start, before the stored workspace is reused or a new one is created, a dispatcher folder inside the plugin data folder, holding it, or whose parent holds it makes `dispatcher.start` fail with `START_FAILED` and is logged. It is checked as given; then on where its existing part really leads (the real path of its deepest existing ancestor plus the rest, so a linked `flowly-dispatcher` creates nothing in the data folder; a link on the way that points nowhere is refused too) before any folder is made; and again on the real path once it exists (so a folder replaced by a link is refused, reuse included).
- The stored workspace is reused while Paseo still returns it, it is not being archived and its directory is the dispatcher folder (after resolving symlinks); otherwise a new one is created on the dispatcher folder and its id replaces `workspaceId`.
- An earlier dispatcher worked in `<dataDir>/dispatcher/`. A stored workspace there is not reused: the next start creates the workspace on the dispatcher folder. That start follows §3 as any other (refused while the stored session is alive; a dead one is replaced). Flowly never moves or deletes the old folder, and never archives its workspace. A dispatcher started there also leaves its Paseo project registered; `ownsRoot` keeps it hidden, and Flowly never removes it.
- Flowly never archives the workspace: no archive, wrap-up, delete, switch or background-workspace path acts on it. Those paths act only on workspaces bound to a card or on the per-project `Flowly background` workspaces, and the dispatcher workspace cannot be bound to a card (New task with an existing workspace refuses the stored dispatcher workspace and any workspace whose directory is the dispatcher folder or the old `<dataDir>/dispatcher/`).
- Its folder, and the old `<dataDir>/dispatcher/`, never become a Flowly project: the Paseo project rooted there and its workspaces are left out of the resources Add project and New task list, and Add project (and restore) with that folder is refused ("This is the Flowly dispatcher's folder; it can't be a Flowly project."). The folder is compared after resolving symlinks.
- A host without background workspaces (`workspaces.create` throws "Update the host to use background workspaces.") makes `dispatcher.start` fail with `HOST_UNSUPPORTED` ("Update Paseo to use the dispatcher: this host has no background workspaces."). Nothing is retried and the record is not changed.

## 3. Lifecycle

Each group's dispatcher is one long-lived session: the provider compacts its context as it fills, and the board is its memory (§6). There is no "context full" state and no start-fresh flow; a new dispatcher starts only to recover from a dead one. A group's dispatcher starts only from **Start dispatcher** (creating a group, and the migration, start none). Every predicate below (`isDeadDispatcher`, `DISPATCHER_RUNNING`, `DISPATCHER_GUARDED`, `DISPATCHER_CHANGED`, unguarded, new-tools) is evaluated for that group's stored session only: one group's session is never replaced because another's is dead. `status`, `start` and `replace` take `groupId` (an unknown group is `GROUP_NOT_FOUND`). Starts, replaces and group deletes share one queue for the workspace, so two groups starting at once create the workspace once.

A stored session is **dead** when Paseo does not return it or it is archived (one predicate, `isDeadDispatcher`). Every other status is the live dispatcher, `closed` and `error` included. Ruling (Noah, 2026-11-09): dead = archived or missing; a stopped (closed) session is resumed, not replaced. The same holds for a card's session and its asks (§9.4): one restored from the archive is alive again, so its asks the chat recorded as `session_ended` come back as live asks (open, counted, answerable) until it is archived again. `closed` means Paseo stopped the idle process (after an hour idle, or on a daemon restart); notes and the user's messages are delivered to it as to an idle one, which resumes it, and Start refuses. A dispatcher in `error` is never replaced automatically either (ruling, Noah 2026-11-09); the user can archive it to start a new one.

`status` → `{ state, agentId }`:

| state | when |
|---|---|
| `none` | the record has no `agentId` |
| `ended` | the stored session is dead |
| `running` | status `running` or `initializing` |
| `idle` | otherwise (including `closed` and `error`) |

`start({ provider?, modeId? })`:

- Refused with `DISPATCHER_RUNNING` unless the stored session is dead (or there is none): there is one dispatcher. Concurrent starts run one after another.
- Opens the workspace (§2) and chooses a new agent id. When a dead session is stored, Flowly reads it again just before replacing it: if it is no longer dead the start is refused with `DISPATCHER_RUNNING` and nothing changes. Start never archives a dispatcher session, and Flowly never archives its workspace.
- Writes the record (new `agentId`, `startedAt` now, the old id added to `previousAgentIds`) before Paseo creates the session, so the session's first tool calls already pass §4. If Paseo did not create it (the agent is not found after the error), the record goes back to the previous `agentId`/`startedAt`/`previousAgentIds` and the error is returned.
- The model: a passed `provider` (`provider/model`, with the passed `modeId`) wins; otherwise the group's `defaults.dispatcherModel`; otherwise the **Dispatcher model** setting (Settings → Models, stored as `dispatcherModel` in the host `models` settings: provider, model, optional reasoning and permission mode); when it is empty or unreadable, the server default `claude/claude-sonnet-5-5` (plan Q6). An unreadable setting is logged.
- The session: that model (`provider/model`, `modeId`, `thinkingOptionId` from the setting's reasoning), system prompt `dispatcherCharter` of the group (§6), title `Flowly dispatcher · <group name>`, labels `flowly-dispatcher=1` and `flowly-dispatcher-group=<groupId>`, first message the board summary (§6), and one saved MCP server, `flowly-dispatcher` (§4), with every dispatcher tool preapproved except the confirmed ones (§5.2).
- Its own tools never prompt (Noah's request, 2026-11-09), except the confirmed tools of §5.2: the `flowly-dispatcher` server is saved in the session's config at create, with a tool policy that preapproves each other tool of §5 by exact name (`{ kind: "mcp", server: "flowly-dispatcher", tool }`), Paseo's supported preapproval. Their writes are already gated by the *Agents create and edit cards* switch and the hourly limits (§5). The entry carries the running tool service's URL and the sealed credential for that `agentId`/`workspaceId`; both stay valid across daemon restarts (the service reuses its port; the credential does not expire), as for card sessions. Paseo checks that every preapproved tool's server is in the same create request. The record notes the saved tool names (`savedTools`); a start Paseo refuses fails with its message and the earlier record is kept (`START_FAILED`).
- Saved tools are fixed when the session is created. While the stored dispatcher is running or idle and its `savedTools` lacks a preapproved tool this build lists (the confirmed tools of §5.2 never count: no session saves them, and a dispatcher started before them lists them from its server and prompts for them as a new one does), `dispatcher.status` adds `newTools: true` and the chat shows a warning: the dispatcher started before some Flowly tools existed, and **Replace dispatcher** archives its session and starts a new one with them, with the same button and confirm as the unguarded warning (one button when both apply, under the unguarded warning). Nothing restarts it on its own. Ruling (Noah, 2026-11-09): Replace dispatcher also takes a guarded dispatcher that misses this build's tools; `dispatcher.replace` refuses with `DISPATCHER_GUARDED` only a guarded dispatcher that has every tool. A dispatcher served by the open hook always has the current tools.
- Claude only (ruling below): the provider part of `provider/model` must be `claude`. Any other provider (Codex, OpenCode, Copilot, ACP, custom ones such as `my-claude`) is refused with `DISPATCHER_PROVIDER_UNSUPPORTED` before anything is opened or written: the workspace, the record and Paseo are untouched. Its message says why and what to pick: "The dispatcher runs only on Claude: on other providers Flowly can't keep it from answering cards' questions and permission requests. Choose a Claude model for the dispatcher in Settings → Models." Any other permission the dispatcher meets is not preapproved; it waits for the user's choice in the dispatcher chat (§9).
- The session-open hook adds no server to a dispatcher saved with its tools: Paseo refuses an open when a plugin adds an MCP server whose name is already in the agent's saved configuration ("MCP server … from plugin flowly collides with agent saved configuration"). Only a stored dispatcher whose record lacks `savedTools` (started before this rule) gets `flowly-dispatcher` from the hook at each open, without preapproval. No other session gets it. The hook stops at the stored dispatcher's session either way: it never gets the card context or the board tools of §2.2 of AGENT-CARDS-SPEC.
- No route to a card's ask: only the user answers a card's questions, permission requests and blockers, with the ask's buttons and answer box in the Flowly UI (§9.4). None of the dispatcher's tools (§5) answers an ask; its one message tool, `flowly_message_card` (§5.3), refuses a session that has one open and never answers. Paseo adds its own agent tools (server `paseo`) to every session; among them `respond_to_permission` answers a request, `send_agent_prompt` messages a session, and its terminal, schedule, mode and agent tools reach a shell or another agent that could; a shell reaches the `paseo` CLI. A dispatcher is therefore created with the session's `providerOptions.disallowedTools` (the SDK's config `options`) = `dispatcherWithheldTools`: the `paseo` server (by its rule and by each tool name of Paseo 0.15.2), Bash and its shell tools, and subagents. Claude withholds them in every mode. Claude Code's own built-in tools also reach other sessions and agents (SendMessage, ListAgents, Workflow, RemoteTrigger, the Cron tools, Skill) and the disk (Write, Edit), and new ones keep coming, so its built-in tools are an allowlist: `providerOptions.extraArgs.tools` = `dispatcherBuiltinTools` (Claude Code's `--tools`): Read, Glob and Grep (to read a project's code for a card), WebSearch (runs on Anthropic's side, never reaching the local daemon; WebFetch is left out) and ToolSearch (loads deferred MCP tool schemas, so its own tools stay callable). MCP servers load only from what Paseo passes: `providerOptions.extraArgs["strict-mcp-config"]` = `null` (a bare `--strict-mcp-config`) keeps the servers Paseo sends (its own and its plugins', so the eight Flowly tools and chat_polish's stay) and drops every server from Claude Code's own user, project, local, plugin and claude.ai configuration, any of which could reach Paseo or another agent under a name the withheld list does not cover. Paseo keeps these options on resume, refresh and daemon restart (from the agent's stored config). Other providers have no per-session way to withhold tools, so the dispatcher does not start on them (above). A dispatcher created before this rule keeps its tools until it is replaced (its config is fixed at creation). The record notes the guard it was started with (`guard`, §1); `dispatcherGuardVersion` is raised whenever the withheld or allowed tools change in a way an older session should not keep. While the stored dispatcher is running or idle and its `guard` is absent, of another version, or on a provider other than Claude, it is *unguarded*: `dispatcher.status` adds `unguarded: true`, it gets no board notes (§7), and the chat shows a warning (the dispatcher can still answer cards' questions and permission requests, and gets no board notes until it is replaced) with a **Replace dispatcher** button. A refused create restores the earlier record's `guard`.
- Ruling (Noah, 2026-11-09): the dispatcher never answers a card's asks, even when the user tells it to; only the ask's buttons and answer box do. There is no relaying tool: the dispatcher has no route to an ask (above).
- Ruling (Noah, 2026-11-09): card sessions keep Paseo's agent tools (`respond_to_permission`, `send_agent_prompt`), so a card's agent could answer another card's asks. The charter forbids the dispatcher to create or start a card, or word its description, so that its agent answers, approves or dismisses another card's questions, permission requests or blockers (§6); that instruction, and the user seeing every card the dispatcher makes, are the guard. No tool is withheld from card sessions.
- Ruling (Noah, 2026-11-09): an unguarded dispatcher gets no board notes; they stay held as for a running one, and it is never woken for them (no send, no re-check), so a fresh dispatcher's board summary covers them. **Replace dispatcher** is the only way Flowly archives a dispatcher: the user's click, after a confirm, calls `dispatcher.replace { agentId }` (a plugin RPC; the dispatcher's own MCP server has no such tool). It is refused with `DISPATCHER_GUARDED` for a guarded dispatcher that has every tool of this build (one that misses tools is replaced, ruling above) and with `DISPATCHER_CHANGED` when the stored session is not `agentId` (or there is none); otherwise, in the same queue as Start, it starts a new guarded dispatcher as Start does (the Dispatcher model setting; the archived id joins `previousAgentIds`), archiving exactly that session (unless it is already dead) once the folder, workspace, MCP server and board summary are ready: when one of them fails nothing is archived and the old dispatcher stays (a workspace Paseo did make is kept in the record, as for Start). The archive comes before the new session is stored, so a crash or a failed save after it leaves the record naming the archived session: ended, never a live session Flowly no longer tracks. A failed archive is logged, refused with `REPLACE_FAILED`, changes nothing in the record, keeps the held notes, and nothing starts. When the session create fails after the archive, the record names the archived session again, so the dispatcher reads as ended and Start works; the error says the old one was archived, and the confirm dialog says so beforehand. Flowly never archives a dispatcher on its own, and Start still refuses a live or closed one.
- Ruling (Noah, 2026-11-09): an unguarded dispatcher takes no messages from the user either, until Replace. The daemon is the gate: `dispatcher.send` (the chat's message box) and `dispatcher.what-next` refuse it with `DISPATCHER_UNGUARDED` and send nothing, and What should I do? then marks nothing seen. While it is unguarded the whole chat is off until Replace: the panel disables the message box, **Ask dispatcher** (the Attention tab, §9.2) and the controls of the dispatcher's own permission requests and questions, and shows "Replace the dispatcher to keep chatting" next to **Replace dispatcher**. The composer queue never holds a message for the dispatcher (it takes only a card's session, and no card is bound to the dispatcher's workspace, §2). Two routes do not pass through Flowly and it cannot block them: Paseo's own view of the dispatcher session (a message or a permission answer typed there), and a card session's Paseo agent tools (`send_agent_prompt`), which can message any session.
- Ruling (Noah, 2026-11-09): the dispatcher is created with `--strict-mcp-config` (above): it loads its Flowly tools (§5), chat_polish and the other servers Paseo passes, and no user, project, plugin or cloud MCP server; this holds on resume as `--tools` does. `dispatcherGuardVersion` is 2 for it, so a dispatcher started without it is unguarded.
- Group delete (`groups.delete`, BOARD-GROUPS-SPEC §2), on the same queue as Start and Replace. The group's existence, revision and non-default state are checked first, so a delete the store would refuse archives nothing. Then: refused while that group's dispatcher is `running` or `initializing` (`DISPATCHER_RUNNING`); a record that cannot be read is `DISPATCHER_UNAVAILABLE`; a live session is archived (a failed archive refuses the delete with `DELETE_FAILED`, nothing changes, logged); then the record is written (entry removed, its ids kept in the global `previousAgentIds`), then the board (projects moved to the default group, group removed), then the group's in-memory notes are dropped and its projects' held notes move (§7). A dead, ended or absent session is not archived. A crash between the record and the board write leaves a group with no dispatcher entry, which reads as `none`. A migrated v1 session still `unassigned` that would move to the deleted group refuses the delete (`DISPATCHER_UNAVAILABLE`). A start that finishes after its group was deleted does not write its entry back and its session is archived, as a refused create is. Ruling (Noah, 2026-11-10): deleting a group archives its dispatcher session (the delete confirm says so, as Replace dispatcher's does). This is Flowly's second dispatcher-archive path, always an explicit user click (the user's `groups.delete`; the tool's `delete` refuses a group with a live dispatcher, §5.2). Flowly still never archives the workspace and never archives a dispatcher otherwise.
- Ruling (Noah, 2026-11-09): the dispatcher starts only on providers that can withhold those routes, Claude today. Start on any other provider is refused with `DISPATCHER_PROVIDER_UNSUPPORTED`, and the Dispatcher model picker offers only those providers; a stored setting on another provider shows the same explanation as a notice above the picker.

## 4. Credential and caller check

- The `flowly-dispatcher` server's bearer token is sealed with purpose `dispatcher` over `{ agentId, workspaceId, groupId }`; `groupId` is optional in the identity schema, because the migrated v1 session's token (saved in its MCP header at creation) has none. `authenticateAny` returns `kind: "dispatcher"` for it. A card (`session`) or board token is never accepted as a dispatcher token and vice versa.
- A dispatcher token gets the dispatcher tools (§5) only: none of the card-session tools, none of the board tools, and not the CLI endpoint (`/api` refuses it).
- Every call checks, in order: the caller's group is found from the record entry that holds the token's `agentId` (a token with a `groupId` must also match it); the token's `agentId` equals that group's stored `agentId` and its `workspaceId` the entry's workspace (§1; never the top-level one) (else `DISPATCHER_REPLACED`; a deleted group, or an `agentId` no entry holds, is `DISPATCHER_REPLACED` too); Paseo returns that agent, not archived, in that workspace (else `SESSION_MISMATCH`).
- Every write (`flowly_create_card`, `flowly_update_card`, `flowly_set_linear`, `flowly_clear_linear`, `flowly_start_card`, `flowly_link_cards`, `flowly_propose_idea`, `flowly_update_idea`, `flowly_message_card`, `flowly_create_project`) is refused with `AGENT_CARDS_DISABLED` while the **Agents create and edit cards** setting is off; reads stay allowed.
- Every tool with a `projectId` first checks that the project belongs to the caller's group (read from the board on each call, so a project that moved to another group between two calls is refused the same way), else `PROJECT_OUT_OF_GROUP`. A write checks it again when it is stored (in the same board transaction as the change; `flowly_start_card` also when the card moves to its worktree and just before the session is made), so a move during the call is refused the same way and writes nothing (a card create may leave its new workspace, as for any create that fails at the write); `flowly_message_card` stores nothing and is checked at the call only; a card id must belong to such a project. Then it checks the project: unknown → `NOT_FOUND`; archived → `PROJECT_ARCHIVED`. A write also needs its root (`primaryPath`) to be a readable directory, else `ROOT_UNAVAILABLE`; reads (`flowly_list_cards`, `flowly_get_card`, `flowly_list_ideas`) of a project whose root is missing are allowed. A card id must belong to that project (`CARD_NOT_FOUND`). Refusals write nothing.
- Every call checks, in order: the token's `agentId` equals the stored `agentId` and its `workspaceId` the stored `workspaceId` (else `DISPATCHER_REPLACED`); Paseo returns that agent, not archived, in that workspace (else `SESSION_MISMATCH`).
- Every write (`flowly_create_card`, `flowly_update_card`, `flowly_set_linear`, `flowly_clear_linear`, `flowly_start_card`, `flowly_link_cards`, `flowly_propose_idea`, `flowly_update_idea`, `flowly_archive_card`, `flowly_create_project`) is refused with `AGENT_CARDS_DISABLED` while the **Agents create and edit cards** setting is off; reads stay allowed.
- Every tool with a `projectId` then checks the project: unknown → `NOT_FOUND`; archived → `PROJECT_ARCHIVED`. A write also needs its root (`primaryPath`) to be a readable directory, else `ROOT_UNAVAILABLE`; reads (`flowly_list_cards`, `flowly_get_card`, `flowly_list_ideas`) of a project whose root is missing are allowed. A card id must belong to that project (`CARD_NOT_FOUND`). Refusals write nothing.
- A legacy multi-repo project (more than one stored `repos`, SINGLE-ROOT-SPEC) follows the same rules as the card agents' tools there: its cards can be created, edited, linked and started, and ideas proposed (SINGLE-ROOT-SPEC §21 lets users edit legacy cards; the read-only rule covers its scope data).

### 4.1 A started card leaves Backlog and Todo (2026-11-12)

Applies to every start of a card's session, a dispatcher's `flowly_start_card` included (START-CARD-SPEC §5) and the board's own starts (drawer Start session, New task, Quick task, via `prepareSession`).

- A card still in Backlog or Todo moves to the project's active-work lane, chosen by role (`startedStatus`, `shared/lanes.ts`): Development when that lane is enabled, else the first enabled work lane (Design, Test); no work lane enabled leaves the card where it is. Never by lane id, and it works when Backlog or Todo is not in the workflow.
- Any other status stays: a card already in a work stage, In review, Committed or Integrated is never moved, never backwards; Blocked, Done and Cancelled are left alone; an archived card does not move.
- The move is one write (`server/start-stage.ts`): revision +1, a `status_changed` event by actor `system` with note "Session started". It runs after the session exists for `flowly_start_card` (a failed start leaves the card in place) and after `prepareSession` for the board's starts (the board creates that session itself afterwards). A failed move is logged and never fails the start.
- The card's own `flowly_update_status` is unchanged and still overrides the stage.
- Why: sessions that never call `flowly_update_status` (the eight "Move Loadout memory into…" cards: their event logs hold progress, tags, workpad and memory writes but no `status_changed`; nothing was refused) left a started card in Backlog.

## 5. Tools

All take `projectId` explicitly, except `flowly_list_projects` and `flowly_create_project`. Writes are recorded with `actor: "agent"` and the dispatcher's `agentId`.

Hourly limit (a runaway brake): the dispatcher's card creations and `flowly_start_card` starts count together, at most 40 in the last hour per dispatcher session (so per group), else `CARD_LIMIT`; the 5 project creations (§5.2) and the group tool's 10 calls are buckets of the same session. This bucket is the dispatcher's own: it neither uses nor fills the card agents' 20 per session (AGENT-CARDS-SPEC §3.3). A plugin reload resets it.

| Tool | Does |
|---|---|
| `flowly_list_projects` | The group's live member projects: `projectId`, `title`, `rootAvailable`, `openCards` (not archived, not Done/Cancelled). |

### 5.1 Ideas

An idea of the project is any idea whose `projectId` is that project: project ideas (no `taskId`) and ideas proposed on its cards. Statuses are the stored ones: `open`, `accepted` (became a card or continued in a card) and `dismissed`.

`flowly_list_ideas { projectId, status?, tag?, type?, query?, limit? }`, a read (archived or unknown project refused as in §4; a missing root is allowed; works while Ideas are off):

- `status`: `open` (default), `accepted`, `dismissed` or `all`.
- `tag`: only ideas whose suggested tags include it (normalized as a card tag; an invalid one is `TAG_INVALID`). `type`: only ideas of that card type.
- `query`: at most 200 characters; only ideas whose title or detail contains it, case-insensitively. Blank matches all.
- `limit`: 1–200, default 50.
- Order: the Ideas page's default (newest first: `createdAt` descending, then `id` ascending; `shared/ideas.ts` `ideaNewestFirst`).
- Result `{ ideas, truncated }`: each idea has `id`, `title`, `detail`, `rationale`, `context`, `type?`, `priority?`, `tags` (`[]` when none), `status`, `scope?` (card ideas only; absent stored reads as `new`), `taskId?` (the source card), `acceptedTaskId?` and `createdAt`. `truncated` is true when more ideas matched than `limit`.

`flowly_update_idea { projectId, ideaId, title?, detail?, rationale?, context?, type?, priority?, tags?, addTags?, removeTags?, status?: "dismissed" }`, a write (§4's guards, then `IDEAS_DISABLED` when Ideas are off, then):

- `ideaId` must be an idea of that project, else `IDEA_NOT_FOUND`. The source card's state does not matter: an idea of a Done, Cancelled or archived card can be edited and dismissed like any other (ruling, Noah 2026-11-09; the Ideas page treats those ideas as live too).
- The same rules as a card session's `flowly_update_idea` (IDEAS-SPEC §3.1, through the same edit code): only the given fields change; an accepted idea cannot change (`IDEA_CLOSED`); a dismissed one cannot be edited (`IDEA_CLOSED`) and dismissing it again changes nothing; edits and a dismissal can come in one call. No field and no `status` is `INVALID_INPUT`; empty `addTags` and `removeTags` count as no field.
- Tags: `tags` replaces the suggested tags (`[]` clears them); `addTags` adds tags not there yet and `removeTags` removes those that are (a missing one is ignored). `tags` together with `addTags` or `removeTags` is `INVALID_INPUT`; a tag in both `addTags` and `removeTags`, an invalid tag or more than 12 tags is `TAG_INVALID`. Ideas' tags carry no origin, so any tag can be removed.
- A new title equal (trimmed, case-insensitive) to another open idea's in the same group is refused: `IDEA_DUPLICATE` on the same card, `DUPLICATE_IDEA` among the project ideas.
- A card idea's change writes `idea_edited` / `idea_dismissed` events on its card with `actor: "agent"` and the dispatcher's `agentId`; a project idea's writes none (PROJECT-IDEAS-SPEC §3).
- Result `{ idea, changed }`: the idea as `flowly_list_ideas` shows it, and whether anything was written.

`flowly_create_card { …, ideaId? }`: the card is created from that idea exactly as the user's New card from an idea (IDEAS-SPEC §6, PROJECT-IDEAS-SPEC §3): the idea becomes `accepted` with `acceptedTaskId`, the card gets `origin.ideaId` (and `origin.taskId`, the source card, for a card idea), and a card idea also adds the `derived` link to its source card and an `idea_accepted` event there. The title and description are the dispatcher's own; nothing is copied from the idea. Checked before anything is created or a slot of the hourly limit is taken: Ideas off is `IDEAS_DISABLED`; an unknown idea or one of another project is `IDEA_NOT_FOUND`; one that is not open is `IDEA_CLOSED`. An idea taken up or dismissed after that check (two creates from one idea at once) is also `IDEA_CLOSED`, and the slot is given back. A retry with the same `idempotencyKey` returns the card already created; the same key with another `ideaId`, or with one where the first call had none (or the reverse), is `REQUEST_REUSED` and leaves the idea as it is.

### 5.2 Confirmed tools

- Ruling (Noah, 2026-11-10): the dispatcher's tool that creates projects is not preapproved. Unlike its other Flowly tools, which never ask (§3), each call shows the provider's permission prompt in the dispatcher chat (§9.3), so the user confirms every project creation. It stays out of the session's `toolPolicy.preapproved` and out of `savedTools` (`dispatcherConfirmedToolNames`, `shared/dispatcher.ts`), so it never raises the new-tools warning (§3); the guard and the unguarded warning do not depend on it.
- Ruling (Noah, 2026-11-10): Flowly enforces "always prompts" where it can. Before anything is written, `flowly_create_project` reads the dispatcher session's current permission mode (`currentModeId` of the agent snapshot Paseo returns for it) and runs only in a mode where Claude asks the user before a tool that is not preapproved: Paseo's Claude modes `default`, `acceptEdits` and `plan` (an allowlist). Any other mode (`bypassPermissions`, `auto`, an id Flowly does not know) and a session that reports no mode are refused with `CONFIRMATION_UNAVAILABLE`; the message tells the user to switch the dispatcher to a mode that asks.
- Ruling (Noah, 2026-11-10): at most 5 project creations per hour per dispatcher session (`PROJECT_LIMIT`), a bucket of its own, apart from the 40 cards and starts of §5. A refused creation gives its slot back. A plugin reload resets it.
- Ruling (Noah, 2026-11-10): on the dispatcher's path only, a project root that is inside, equal to or holds Flowly's plugin data folder or the dispatcher's parent folder (`<Paseo home>/flowly-dispatcher`, §2) is refused (`PROJECT_REFUSED`), compared on canonical (real) paths, so a link to one of them, `~` and `/` are refused too. The project form's `projects.create` keeps its own rules (only the dispatcher's folder itself is refused there, §2).
- Ruling (Noah, 2026-11-10, superseded the same day by BOARD-GROUPS-SPEC v2): there was no board-group tool because board groups lived in host settings, which the daemon side of the plugin SDK can only read. They moved into board data, so `flowly_manage_groups` (below) writes them without a local-daemon exception.
- `flowly_manage_groups` (implemented by the manage-groups card; confirmed, not preapproved, not in `savedTools`; same mode check `CONFIRMATION_UNAVAILABLE`, `AGENT_CARDS_DISABLED` gate and `PASEO_UNAVAILABLE` order as `flowly_create_project`): `{ action: "create" | "rename" | "set_members" | "set_default" | "delete", groupId?, name?, projectIds? }`. It may act on **any** group (ruling, Noah 2026-11-10) and goes through the same functions as the `groups.*` RPCs (BOARD-GROUPS-SPEC §2), so it also takes the target's `revision` and a stale one is refused. `set_members { groupId, revision, projectIds }` replaces the member list: listed projects move in from their current groups, and a current member left out goes to the default group (so no project is ever groupless); on the **default** group it may only add (leaving a member out is refused, `DEFAULT_REQUIRED`). Refusals: deleting the caller's own group (`GROUP_PROTECTED`), the default group (`DEFAULT_REQUIRED`), a duplicate or invalid name, an unknown group or project (`NOT_FOUND`), an archived project. `delete` of a group whose dispatcher session is live (running, idle or closed) is refused by the tool with `GROUP_BUSY` (Flowly's own archive must follow an explicit click, and the provider prompt can be skipped by an allow rule): the user deletes such a group in the UI, where the confirm says its dispatcher is archived. At most 10 calls per hour per session (`GROUP_LIMIT`, a bucket of its own, refusals give the slot back). It is in `dispatcherConfirmedToolNames`, never in `dispatcherToolNames`, so it never raises the new-tools warning.
- Not enforceable by Flowly: an allow rule in the user's or a project's Claude settings that covers the tool, and a client's "always allow" answer to its prompt, both skip the prompt without changing the session's mode. The mode can also change between the check and the call. The user owns those choices.
- `flowly_create_project { path, title?, description? }` → `{ projectId, title, path }`:
  - `path`: 1–4096 characters, not trimmed (as in `projects.create`); an absolute path, `~/…` (the user's home) or `~` alone (the home folder, then refused by the rule above in a normal install). A relative path is refused as invalid input: the daemon's working folder is not the user's. An existing folder, usually a Git repository; no Git check beyond the project form's. `title`: 1–120 characters after trimming, default the folder's name (its last part after resolving links, trimmed and cut to 120), or `Project` when that is empty (`/`, a name of spaces). `description`: up to 10,000 characters, default empty. Other fields (linked-project `links`, `paseoProjectId`) are refused as invalid input.
  - The new project is placed in the caller's group (`groupId` passed to the `projects.create` path).
  - Checked in order: the input; the caller (§4); `AGENT_CARDS_DISABLED` while *Agents create and edit cards* is off; `PASEO_UNAVAILABLE` (retryable) before the plugin entry has handed over the RPC's path; `CONFIRMATION_UNAVAILABLE`; `PROJECT_LIMIT`. None of them writes anything.
  - Then the folder is canonicalized and checked against the reserved folders above, and the default title made; then exactly the `projects.create` RPC's path (the project form's Create project with *Single directory*), one function shared by both (`projectCreator`, `server/project-create.ts`): the same board service call, serialized with the form's, and its follow-up (the new project's check commands detected for its guardrails, GUARDRAILS-SPEC §4.5). The folder is refused when it is the dispatcher's folder (§2), matched to a native Paseo project at that root or registered as one (`paseo project create`), and refused when that native project is already on the board. The project is written as that RPC writes it (one root, `revision` 1, Auto review on). It does not restore a project saved in the folder's `.flowly/` (PROJECT-FOLDER-SPEC); the form offers that, the tool does not.
  - Every refusal after the input check and the guards above is `PROJECT_REFUSED` with its message: "Expected an existing directory." (missing, or not a folder), the reserved-folder refusal, "This is the Flowly dispatcher's folder; it can't be a Flowly project.", "Paseo project is already linked; open or restore its board project.", "Native project root does not match the selected primary directory.", or Paseo's own error. Nothing is written to the board then (a native project Paseo already registered stays, as with the form).
  - Linked multi-repo projects (`projects.create-linked`) are not offered.

### 5.3 Messaging a card's session

- Ruling (Noah, 2026-11-10): `flowly_message_card` is preapproved like the dispatcher's other card tools (§3): it is in `dispatcherToolNames` and `savedTools`, so it never prompts; a dispatcher started before it shows the new-tools warning (§3). Its limit is 30 per hour per dispatcher session (`MESSAGE_LIMIT`), a bucket of its own beside the 40 cards and starts and the 5 projects; a refused or failed send gives its slot back; a plugin reload resets it.
- `flowly_message_card { projectId, taskId, text, sessionId? }` → `{ sent: true, sessionId }`. `text`: 1–10,000 characters after trimming. The card must be live in that project (`CARD_NOT_FOUND`).
- Checked in order, none writing anything: the input; the caller (§4); the write gates of §4 (`AGENT_CARDS_DISABLED`, `NOT_FOUND`, `PROJECT_ARCHIVED`, `ROOT_UNAVAILABLE`); the card; the session; `SESSION_WAITING_ON_USER`; `MESSAGE_LIMIT`; then the send.
- The session: a card's sessions are the not-archived sessions in its workspace, Flowly's own helper runs excluded. With `sessionId`: that one, else `SESSION_NOT_FOUND`. Without: the only live session; with several, the only running (or initializing) one; otherwise `SESSION_AMBIGUOUS`, whose message lists them. No live session: `NO_LIVE_SESSION` (no session is started: that is `flowly_start_card`).
- Never an answer: refused with `SESSION_WAITING_ON_USER` when the target session has any pending request in Paseo's snapshot (a permission or an AskUserQuestion) or an open question or blocker report on the card (`openReport`, §9.4: open until that session's next turn starts). Only the user answers those, with the ask's buttons (§9.4). The send is always steered (`activeTurnBehavior: "steer"`, `userSendOptions`), like the chat's: a send without it interrupts a turn and clears pending permissions (§7). Whether a steer could also resolve a pending request is not relied on: the refusal applies in any case. Remaining race, as §7: a request raised between the read and the send is not seen.
- The message is `dispatcherMessagePrefix` + the text: "From the Flowly dispatcher (an automated assistant, not the user): …", so the card's agent knows the user did not type it. This is an exception to the product invariant "a card's ordinary follow-up sends exactly the user's text" (AGENTS.md), for dispatcher messages only; the user's own sends are unchanged. It is not recorded as a card event; the session's transcript shows it.
- Per group (§0): the tool works for the caller's group's projects only, and its bucket is that group's session's own.
- Charter (§6): use it only for what the user asked or their standing requests cover; never to answer an ask; never to have one card act on another card's asks.
- Errors: `SESSION_WAITING_ON_USER`, `SESSION_AMBIGUOUS`, `SESSION_NOT_FOUND`, `NO_LIVE_SESSION`, `MESSAGE_LIMIT`, `SEND_FAILED` (retryable; Paseo refused the send), and the codes of §4.

### 5.4 Replying to an agent that wrote

- Ruling (Noah, 2026-11-12): the dispatcher may answer an agent that messaged it (Paseo's `agent_message` provenance, the From row of §9.3) with `flowly_reply_to_agent`. It is a narrow exception to the withheld `paseo` server (§3): `dispatcherWithheldTools` is unchanged (no `send_agent_prompt`), so the dispatcher still cannot start a conversation, reach a card's session other than through `flowly_message_card`, or answer anything. Preapproved like the other card tools: in `dispatcherToolNames` and `savedTools`, so it never prompts, and a dispatcher started before it shows the new-tools warning (§3). `dispatcherGuardVersion` stays 2: the guard versions the routes a session is started *without* (withheld tools, built-in tools, strict MCP config), none of which changed; a missing Flowly tool is what the new-tools warning covers.
- `flowly_reply_to_agent { agentId, text }` → `{ sent: true, agentId, note }`. `agentId`: 1–200 characters; `text`: 1–10,000 characters after trimming.
- Answer once (bug fix, 2026-11-12): Paseo notifies a sender that prompted with `notifyOnFinish` (its default) with the dispatcher's final turn text when the turn ends (verified: a finished agent's `agent-response` is its final text). A tool reply followed by a final text that repeats it therefore reached the sender twice. The dispatcher answers through the tool **or** its final text, never both: the charter and the tool description say so, and `note` (`replyOnceNote`) repeats it in every result, telling it not to repeat the reply in its final text. Flowly cannot suppress Paseo's notification; no limit of this section changed.
- Checked in order, none writing anything: the input; the caller (§4); `AGENT_CARDS_DISABLED`; the target is the caller or any recorded dispatcher session (`REPLY_NOT_ALLOWED`); the target sent a prompt the caller's own session received within the last 24 hours (`dispatcherReplyWindowMs`), else `REPLY_NOT_ALLOWED`; the target is live (`AGENT_NOT_FOUND` when Paseo does not list it or it is archived); it is not in a dispatcher workspace nor a card's session (a session in the workspace of any card, archived cards included; `REPLY_NOT_ALLOWED`, whose message points to `flowly_message_card`); `SESSION_WAITING_ON_USER` while it has any pending request in Paseo's snapshot (a permission or an AskUserQuestion; never answered, as §5.3); `REPLY_LIMIT`; then the send.
- Who wrote: Flowly reads the caller's own timeline (projected, as `dispatcher.tail`), newest first, in pages of 200, until it finds an `agent_message` whose sender is the target with a timestamp inside the window, reaches an entry older than the window or the start, or has read 10 pages (2,000 entries). An entry without a timestamp never counts. A failed read is `TRANSCRIPT_UNAVAILABLE` (retryable). The sender's id is Paseo's provenance, which Paseo writes, not the sender's text.
- The message is `dispatcherMessagePrefix` + the text ("From the Flowly dispatcher (an automated assistant, not the user): …"), always steered (`userSendOptions`), as §5.3.
- Limits (a runaway brake against two agents looping): at most 5 replies per answered agent per hour (`dispatcherRepliesPerAgentPerHour`) and 20 per dispatcher session per hour over all agents (`dispatcherRepliesPerHour`), both `REPLY_LIMIT` with the reason in the message; a bucket of its own beside `flowly_message_card`'s 30. A refused or failed send gives its slot back; a plugin reload resets it.
- Record: like `flowly_message_card`, a reply is not a card event and not in Insights; the dispatcher's transcript shows the tool call and the target's transcript shows the message. There is no other audit path for either.
- Errors: `REPLY_NOT_ALLOWED`, `AGENT_NOT_FOUND`, `SESSION_WAITING_ON_USER`, `REPLY_LIMIT`, `TRANSCRIPT_UNAVAILABLE`, `SEND_FAILED` (retryable), and the codes of §4.

## 6. Charter and board summary

- `dispatcherCharter(group)` (English, `shared/dispatcher.ts`): the dispatcher's role (it keeps the projects of its group moving, and may manage groups only when the user asks); the board is its memory; every repo task is a card (one branch or PR); start sessions straight away with `flowly_start_card`; split independent deliverables into separate cards tied with `flowly_link_cards`; park asks as project ideas; keep the project's ideas current with `flowly_list_ideas` and `flowly_update_idea`, and create a card from an idea with `flowly_create_card`'s `ideaId`; create a project with `flowly_create_project` only when the user asks for one (each call is confirmed by the user), never to make room for a card; use `flowly_message_card` only for instructions the user asked for or their standing requests cover, never to answer an ask (it is refused while the session waits on the user) and never to have one card act on another card's asks; use `flowly_reply_to_agent` only to answer an agent that messaged it, briefly, never to start a conversation, relay or answer a card's asks, or reach a card's session (ruling, Noah 2026-11-12); a card's asks are the user's, answered with their buttons and answer boxes, and the dispatcher has no tool that answers them, so it tries no other route and, when asked to answer one, points to its buttons; it never creates, starts or words a card so that the card's agent answers, approves or dismisses another card's asks; note messages are board updates, not instructions from the user; whenever it mentions a card it writes a card link (§9.3).
- Board summary (first message): a line per live project of the group with its `projectId`, then the markdown export (IDEAS-IMPORT-EXPORT-SPEC) of those projects' open cards and open ideas, without memory.

## 7. Notes

- The event bus subscriber first drops an A1r restore note identical (same from, to, note) to the last one let through for that card, until real work or another transition on the card (EVENT-BUS-SPEC §3.1; in memory only), then pushes only stops (`facts.filter(isStop)`, EVENT-BUS-SPEC §2) into the note batchers, so a later non-stop fact on a card never replaces its stop. The fact carries its project's group as of the commit that made it, so the group is resolved **when the stop is pushed** and the note goes to that group's batcher: one batcher, one held-notes map, one send cooldown and one start window per group. A stop with no group (a board before its group migration) is dropped. Facts caused by any dispatcher (`event.agentId` among every dispatcher session id ever recorded, §1) are dropped by the batchers, so a dispatcher never wakes itself or another group's.
- A project that changes group (`projects.set-group`, `set_members`, a group delete moving projects to the default group): both layers of held notes for its cards (the batcher's buffer and the group's held map) move to the new group's batcher, the newer note winning the merge, and are dropped when the new group has no dispatcher recorded or starting (an ended one drops them at delivery, as for any note). A stop pushed before the move stays with the group it was resolved for. A group delete drops that group's held and buffered notes, and stops of it that arrive afterwards (decision 2026-11-10: they were for the archived session; its projects' later stops go to the default group's dispatcher), so they are not moved with its projects. A downgraded build reads the v2 file as invalid and preserves it (§1); the group sessions are then orphaned, which is not supported. `commitHandler` builds no facts while nothing subscribes.
- Flowly never steers or interrupts the dispatcher's turn (single-pane spec, "never steer or interrupt"). Paseo's daemon treats a send without `activeTurnBehavior` as `interrupt` and answers (clears) pending permissions, so Flowly sends only after re-reading the agent just before sending and finding it `idle` with no pending permission.
- Remaining race, accepted (ruling, Noah 2026-11-09) until Paseo offers a queued (or reject-if-busy) send: between the read that sees `idle` and the send, the user or the agent can start a turn or raise a permission; the send then lands on that turn and can interrupt it.
- A batch is delivered by state:
  - `idle`, no pending permission, send cooldown passed → one message with the held notes and the batch, sent without `activeTurnBehavior`.
  - `running`, or `idle` with a pending permission → held in memory, one note per card, until the dispatcher's `agent.turn_ended`, then delivered the same way. When the read at that turn end still holds them (the hook can arrive before Paseo's snapshot changes, and a later turn end may never come), Flowly reads again after 2 s, then 5 s, 15 s, 30 s and every 60 s after that, until the notes go out, the dispatcher dies or the plugin unloads. A batch held while the read says running with no turn end since (one ended with nothing held) is read again after 60 s, and every 60 s after that, by the same rule. A `dispatcher.status` read that sees `idle` also delivers what is held.
  - Send cooldown: no second send within 8 s of the last one (as the composer's queue drain), so a stale `idle` read cannot double-send; a batch inside it is held and sent once it has passed, under the same checks.
  - While a start is under way, from before it takes the board summary until Paseo has created the session (or the start fails) → held; then the held notes are delivered by the dispatcher's state (the new session's, or the one a refused start kept). Notes held when the start began are on the board the summary reads and are not sent again; notes that arrive while it is written are kept, so one may repeat the summary.
  - `running` or `idle`, unguarded (§3) → held, never sent and never re-checked; a Replace (or any start) covers them with its board summary, and notes after it go to the new dispatcher.
  - `none`, `ended` → dropped, held notes too (the next dispatcher's board summary covers them). A live dispatcher never loses notes to its state.
- Held notes for a card merge as the batcher's do (EVENT-BUS-SPEC §3): a question or blocker is kept over a later plain status change (shown as `; then <move>`), anything else is replaced by the newer note, and the count of facts not shown carries over across batches.
- A failed state read drops the held notes and is logged; a send that fails is logged and its notes are dropped, not replayed. Notes that reach Flowly before it has a Paseo connection are dropped and logged ("Flowly dispatcher notes dropped: no Paseo connection yet:"). All with `logFailure` under fixed labels; counts only, no note text.
- Message: `Flowly board update (N cards):` then one line per note: `- "<title>" [<taskId>] in project <projectId>: <kind> — <detail>[; then <later>][ (+N earlier)]`.
- On plugin unload the batcher and the dispatcher's delivery are disposed (timers and pending notes cleared, no later sends) and the subscription removed; held notes lost that way are logged ("Flowly dispatcher held notes dropped on unload:"). Held notes live in memory only.

## 8. RPCs

All `dispatcher.*` RPCs below take `groupId` (an unknown group is `GROUP_NOT_FOUND`), and act on that group's dispatcher.

- `dispatcher.status` `{ groupId }` → `{ state, agentId }` (§3).
- `dispatcher.start` `{ groupId, provider?, modeId? }` → `{ agentId }` (no `provider`: the group's model, else the Dispatcher model setting, §3); errors `DISPATCHER_RUNNING`, `DISPATCHER_PROVIDER_UNSUPPORTED` (a provider other than Claude, §3), `HOST_UNSUPPORTED`, `START_FAILED` (Paseo did not create the session; its reason in the message), returned as the RPC error.
- `dispatcher.replace` `{ groupId, agentId }` → `{ agentId }`: the user's confirmed Replace dispatcher (§3); errors `DISPATCHER_GUARDED`, `DISPATCHER_CHANGED`, `REPLACE_FAILED`, and Start's.
- `dispatcher.items-changed` `{ groupId, etag? }` → `{ etag, value?: ChatItem[] }`: the group's stored items plus the change line (§9.1, §9.2).
- `dispatcher.tail`: the `sessions.tail` input without `taskId`, plus `groupId`, and its output, for that group's stored dispatcher session only; every other session is refused (§9.3).
- `dispatcher.configure` `{ groupId, agentId, thinkingOptionId?, modeId?, stop? }` → `{ applied }`: the message box's chips and Stop, as `sessions.configure` without `taskId` or `title`, for that group's stored dispatcher session in its stored workspace only; any other session is refused ("This session is not the dispatcher."), as are an archived session and a mode the session does not offer. It never touches the dispatcher record, so the guard stands (§3, §9.3).
- `dispatcher.mark-seen` `{ groupId, revision, ids? }` → `{ seenRevision }` (§9.2).
- `dispatcher.send` `{ groupId, text, images?, messageId }` → `{ sent: true }`: the chat's message, steered (§9.3); errors `DISPATCHER_DOWN`, `DISPATCHER_UNGUARDED` (§3).
- `dispatcher.what-next` `{ groupId }` → `{ sent: true }` (§9.2); errors `DISPATCHER_DOWN`, `DISPATCHER_UNGUARDED` (§3).
- `asks.answer` `{ signal, answer: { optionIds?, text?, allow? } }` → `{ delivered, state }` (§9.4).
- `asks.dismiss` `{ signal }` → `{ taskId }` (§9.4).
- `tasks.start-again` `{ taskId, idempotencyKey }` → the `flowly_start_card` result (§9.4). A refusal's message is `CODE: message`.
- `asks.resolved` `{ etag? }` → `{ etag, value?: string[] }`: the signals the chat resolved, sorted (§9.4).

## 9. Chat panel

The dispatcher's chat sits next to the board (single-pane spec, "Design details"): the dispatcher's transcript with Flowly-rendered items interleaved by time. The dock shows the dispatcher of the selected group (the shown project's group, else the default group; Start dispatcher when it has none), and its header names the group.

### 9.1 Items

`<dataDir>/dispatcher-items.json` `{ version: 1, items: ChatItem[] }`, written atomically (temporary file + rename, mode 0600) and serialized; a file that does not parse or validate is renamed to `dispatcher-items.json.invalid-<epoch ms>` and read as empty. `ChatItem` (`shared/dispatcher.ts`) is `{ id, at, kind, … }`:

| kind | stored | holds |
|---|---|---|
| `note` | yes | one dispatcher note (§7), recorded when its batch was sent to the dispatcher; never when the batch was dropped, so the chat shows exactly what the dispatcher received. Stamped with the `groupId` and `agentId` of the session that received it; a group's chat shows only the notes stamped with its group (ruling, Noah 2026-11-10: a note stays with the session that received it when its project later changes group). An unstamped v1 note belongs to the group named by the record's `legacyGroupId` (else the default group), and shows nowhere once that group is deleted |
| `ask` | answered and ended ones; open and dismissed ones are computed on read (§9.4) | a card's ask (`signal`, `taskId`, `projectId`, `title`, `state` open / answered / session_ended / dismissed, `resolvedAt`, and `askKind`, `agentId`, `detail`, `options`, `questions`, `elsewhere` (answered in the session)) |
| `answer` | yes | the user's answer to an ask, addressed to the card (`signal`, `taskId`, `projectId`, `text`, `choice` allow/deny for permissions, `delivered`) |
| `change` | no, computed on read | "Changed since you looked" (§9.2) |

`dispatcher-items.json` stays one file for all groups. On every write the list is pruned: asks answered or dismissed more than 7 days ago (`resolvedAt`, else `at`) are dropped, then the 500 newest items (by `at`) are kept per key: each group's stamped notes, the unstamped notes together, and asks and answers together (they are not shown in the chat, so they have no group, §9.4: the step-through, the bell and the sidebar badge read every group's asks, BOARD-GROUPS-SPEC §3).

### 9.2 Changed since you looked

- The change line, the mark and the "N updated" scope are per group: only cards of the group's live projects count, and a group with no dispatcher entry has no mark and no line (other groups start with none; the migrated dispatcher's group keeps the old mark).
- An event's revision is its time in epoch milliseconds (`Date.parse(event.at)`). The user's mark is `seenRevision` with `seenIds` (the ids of the events at exactly that millisecond already seen) in the group's entry of `dispatcher.json` (§1; absent in older files). While it is absent the dispatcher's `startedAt` is the mark, with no ids; with neither there is no change line.
- The change line counts the cards with an event after the mark (a later millisecond, or the mark's own millisecond with an id not in `seenIds`), by an agent or the system, whose card is not archived and whose project is live. The user's own changes are not news to them, and the dispatcher's own actions (events whose `agentId` is the stored dispatcher session or one of its `previousAgentIds`, §1) are not news either: a dispatcher made them. Its `revision` is the newest such event's millisecond, `ids` the ids of the counted events at that millisecond, its `at` that time, and it lists each card (`taskId`, `projectId`, `title`, `status`, number of events), newest first.
- **Mark seen** (`dispatcher.mark-seen { revision, ids }`, the line's own values) with no `taskId` marks the whole line (the group mark; used by What should I do?). It first clamps `revision` to the daemon's clock (a clamped mark keeps no ids). A later millisecond replaces the mark, the same millisecond adds the ids, an earlier one changes nothing: a mark never moves back, and a change after the line was read, even in the same millisecond, shows again. A new dispatcher keeps the mark.
- The daemon scans the board for the line only when the board's revision or last event, the mark or the dispatcher session changed; an unchanged board costs no scan per poll.
- **What should I do?** (`dispatcher.what-next`) sends the dispatcher `What should I do?` followed by the changed cards (`- "<title>" [<taskId>] in project <projectId>: <status>`), the change line as the daemon reads it at that moment. Once the message was sent, it marks those cards seen with that line's `revision` and `ids`, exactly as **Mark seen** would; a send that fails, or a refusal, marks nothing and the error shows under the line. Refused with `DISPATCHER_DOWN` unless the dispatcher is running or idle; it is sent with `activeTurnBehavior: "steer"`, as the composer's messages are. **Mark seen** stays its own button.

### 9.4 Asks

One source (plan Q1): `asksFrom(board, agents, receipts, dismissals)` in `shared/attention.ts` turns every Attention signal (ATTENTION-DISMISS-SPEC, Signal keys) into one ask. The bell counts the open ones; the dock's Attention tab shows them (ruling below). An ask is `{ signal, taskId, projectId, agentId, kind, title, detail, at, options, questions?, requestId?, state }`:

| kind | from signal | answered in the chat by |
|---|---|---|
| `question_report` | `q:<eventId>`, the session's open Flowly question | typed text, sent to that session |
| `blocker_report` | `b:<eventId>`, the session's open Flowly blocker (plan Q5: open until that session's next turn starts) | typed text, sent to that session |
| `ask_user` | `p:<agentId>:<requestId>` of a pending `question` request (AskUserQuestion) | its options and "Other" text, through Paseo's permission response |
| `permission` | `p:<agentId>:<requestId>` of any other pending request | its provider actions, or Allow / Deny when it has none |
| `error` | `e:…` | not answerable; Open card |
| `unread` | `u:…` | not answerable; Open card |

- `title` is the card's title; `detail` the question or blocker text, the request's title, or empty. `at` is the report's time, else the session's attention time. `options` are `{ id, label }`: for `ask_user` one per question option (`q<i>o<j>`, labelled `header: label` when the form has several questions) with `questions` describing each question (header, text, multi-select, whether it takes text); for `permission` one per provider action (`a<i>`), or `allow` / `deny`.
- A live ask's state is `open`, or `dismissed` when its signal is in the card's dismissal set. An ask's session has ended only when it is archived or gone: such asks are recorded as `session_ended` (below) and shown as Session ended with no answer controls, not open (the bell and the badge leave them out). A stored `session_ended` row counts only while its session is archived or missing: when Paseo lists the session again unarchived (restored from the archive), the row is ignored and the live ask stands, open, counted and answerable. A `closed` session has not ended: Paseo stops an idle session's process after an hour, and on a daemon restart, and a message reloads it. Its asks stay live, open in the chat and the bell, and answering one goes through (the session is resumed for it). Its pending requests went with the process (Paseo clears them on close), so only its question and blocker reports remain. An ask the chat stored as answered, session ended or dismissed is *resolved*: it is not open even while the session still shows its request or report (Paseo drops a request on its next update; a report stays until the next turn). The open asks are the live open ones less the resolved ones (`openAsks`). The bell, the sidebar badge (`attention.count`, from the same `asksFrom` and the chat's stored items) and the chat's open rows are all that number. The board reads the resolved signals with `asks.resolved` (an etag read every 5 seconds while the board is shown), so the bell matches the badge with the chat closed and after a reload. After `asks.answer` or `asks.dismiss` resolves, the client also leaves that signal out of the bell until the board's live list drops it, covering the moments before that read catches up. `error` and `unread` signals are never resolved: their keys are reused (`e:<agentId>:status`, a new unread turn) and must count again when they come back.
- The agent list behind the asks and the badge is shared for 2 seconds per Paseo handle (one listing at a time; a failed one is not kept; an answer or a snooze starts a fresh one), so the badge and the open chat's polls cost one listing. The plugin host gives every RPC the same handle until its daemon connection is re-created; a new handle never reads the old one's list.
- `dispatcher.items-changed` adds the live asks as `ask` items (id `ask-<signal>`). A stored `ask` item with the same signal (answered, session ended or dismissed) wins over the live one. The exception is a stored session-ended item whose session Paseo still lists and has not archived (written while a closed session's asks counted as ended): it is ignored on read, in the chat, `asks.resolved`, the badge and `asks.answer`, and the live state stands; once that session is archived or gone the stored item stands again. Stored `ask`, `answer` and `note` items of a card that no longer exists are left out: a deleted card's asks, answers and notes disappear (notes: ruling, Noah 2026-11-09).
- **Answering** (`asks.answer`, one at a time on the daemon). The input is validated (signal up to 600 characters; up to 100 option ids; text up to 20,000 characters; up to 50 per-question texts). An `e:` or `u:` signal is refused first ("This ask has no answer; open the card."), before any stored or remembered state is read, as is a remembered ask of kind `error` or `unread`. Then, in order:
  1. A stored ask with that signal already answered or ended: `{ delivered: false, state }` with its stored state, no call. A stale or replayed answer never reaches the session again.
  2. The signal is not among the live asks. Unknown to this daemon run: `{ delivered: false, state: "answered" }`, no call. When the card no longer exists the RPC fails ("The card was deleted."). Otherwise its session is read again: archived or gone, the ask is recorded as `session_ended` (it ended with its session, it was not answered); else the session resolved it, recorded as answered in the session.
  3. The session is read again from Paseo. Archived or gone: `{ delivered: false, state: "session_ended" }`, recorded; Flowly never restores it. Closed: answered as below (Paseo reloads it). In another workspace than the card's: refused, nothing is sent.
  4. By kind: `ask_user` and `permission` need the request still pending in that session (else step 2's answer). A `permission` ask with no request (Paseo cleared a closed session's requests; its signal is `p:<agentId>:<attention time>`) has nothing to approve: when the session is `closed` it takes the user's typed text instead, sent exactly as typed with `activeTurnBehavior: "steer"` (which resumes the session), and empty text is refused; in a session that is not closed it is refused ("Open the card to answer this request.") and nothing is sent. `ask_user` builds the reply with the session pane's rules (`answerReply`); every question must be answered. Typed answers come one per question (`texts[i]`, a box under each question that takes text); a single `text` is accepted only when exactly one question takes text. Typed text is never dropped: text for a question that takes none, or text plus an option on a single-choice question, is refused. `allow: false` declines with `dismissReply`; the recorded `choice` is what that reply did (a form of free-text questions that accept empty answers submits empty, an allow, never shown as denied). `permission` takes exactly one option id, or `allow` when the request has no provider actions; an option's behavior comes from the request, never from the client, and nothing is allowed without the user's explicit choice. `question_report` and `blocker_report` need the report still open and send exactly the user's text (`activeTurnBehavior: "steer"`), no task header (product invariant). `error` and `unread` are refused.
  5. Only after the Paseo call resolves: the ask is stored as answered and an `answer` item (`text`, `choice` allow/deny for permissions and declines, `delivered: true`) is added, and `{ delivered: true, state: "answered" }` is returned. A failed call records nothing and fails the RPC.
  - Known limit: a delivered answer is remembered in memory for the daemon run and in the chat file. A report answer can be sent a second time after a daemon restart when recording it failed, or when its stored item was pruned (§9.1) while the report was still open; permissions and AskUserQuestion requests cannot, since Paseo no longer lists the answered request.
- **Snoozing** (`asks.dismiss`) adds that one signal to its list's dismissal set on the card (ATTENTION-DISMISS-SPEC, RPC); the bell's count drops by one, and the card leaves the bell when all its need-you signals are snoozed. The snooze is per list: a Needs you snooze never touches the card's unread turn in Updates. Snoozing the card's Needs you list from its menu snoozes all its need-you asks in the chat. An ask whose session ended can be snoozed too: it is stored as `dismissed` in the chat (and its signal added to the dismissal set when it is still live). Any other ask that is no longer live is refused ("This ask is no longer open.").
- **Start again** (`tasks.start-again { taskId, idempotencyKey }`): the `flowly_start_card` path (START-CARD-SPEC §3) started by the user: not gated by the agent-cards setting or its hourly limit; every non-archived session counts as the card's, `closed` included (ruling, Noah 2026-11-09: a closed session is resumed by a message, not replaced), so a running, idle or closed one refuses with `CARD_HAS_SESSION`; the session is labelled `flowly-started-by: user`; a workspace move is recorded as the user's. Refusals reach the chat as `CODE: message`; the chat shows `NEEDS_WORKTREE` ("This card's folder already had sessions, or Flowly didn't create it for the card. Switch the card to a worktree from its menu, then start again.", covering both causes) and `CARD_HAS_SESSION` ("The card already has a running session. Send it a message instead.") in the user's words and language, and any other refusal by its message.

## 10. Acceptance

- Starting a card in Backlog or Todo (`flowly_start_card` and `prepareSession`) moves it to Development; a card in Development, Test, In review or Blocked, or Done, Cancelled or archived, stays; with Development disabled it moves to the first enabled work lane (§4.1).
- Per group: start, replace, status and `DISPATCHER_RUNNING` are per group on one queue; a dead group's dispatcher is not replaced by another group's start; two groups starting at once create the workspace once; a token of group A is refused on group B's projects (`PROJECT_OUT_OF_GROUP`), also after a project moved; an old token without `groupId` works through the record, a deleted group's is `DISPATCHER_REPLACED`; the hourly buckets are independent per session.
- v1 migration: the old session lands on the group with the most open cards (ties: first), keeps every field, other groups read `none`; with no group it waits as `unassigned`; running it twice changes nothing; an unknown or invalid file is preserved.
- A repeated A1r restore on a card notifies once; real work or another transition on the card re-arms it (EVENT-BUS-SPEC §3.1).
- Notes are routed by the project's group when the stop is pushed, one batcher, held map, cooldown and start window per group; after a project moves, its held notes follow (dropped when the target has no dispatcher); `exclude` covers every recorded session id; chat notes are stamped and each chat shows only its own session's notes (unstamped v1 notes: the migrated group); the 500 cap is per key.
- Group delete: refused while that dispatcher is running; archives only that group's session and never the workspace, in the order archive, record, board; a failed archive is `DELETE_FAILED` and changes nothing; a start that finishes after its group was deleted writes nothing back.

- A dispatcher token can write to any live project; an archived project is refused with `PROJECT_ARCHIVED` and nothing is written; a token from a replaced dispatcher is refused.
- Card and board tokens cannot call dispatcher tools; a dispatcher token cannot call card-session or board tools.
- Start creates a background directory workspace once on the dispatcher folder (outside the plugin data folder, its parent holding nothing else) and reuses it; Flowly never archives it. A stored workspace in the old `<dataDir>/dispatcher/` is not reused, and that folder is left as it is.
- A started dispatcher's session is created with the `flowly-dispatcher` server saved, exactly the tools that credential lists preapproved on it, and `dispatcherWithheldTools` disallowed; its open adds no server. A dispatcher stored without `savedTools` gets the server from the open hook.
- Start on any provider other than `claude` (Codex, OpenCode, Copilot, ACP, custom, `my-claude`) is refused with `DISPATCHER_PROVIDER_UNSUPPORTED`, whether passed or from the Dispatcher model setting; nothing is created and the record is unchanged. The chat shows the translated explanation. The Dispatcher model picker lists only Claude, and a stored setting on another provider shows the explanation.
- Start is refused while the stored session is alive (running, idle, closed, error, any context use); a dead one (archived, missing) is replaced after a re-read still finds it dead, and nothing is archived.
- A closed (not archived) dispatcher reads as `idle`: notes and the user's messages are delivered to it (Paseo resumes it), and the chat header shows it as Asleep, not ended.
- Notes wait for the turn to end and never steer; a pending permission holds them like a running turn; a turn end read as still running is re-checked with a growing delay until the notes go out; a second send waits for the cooldown; notes in the start window, from the board summary on, are held until the session exists; a batch held while running with no turn end is re-checked every 60 s; notes are dropped only while the dispatcher is dead or missing.
- A legacy multi-repo project takes the dispatcher's writes under the card agents' rules (no legacy refusal).
- With Agents create and edit cards off, every dispatcher write (links and ideas included) is refused with `AGENT_CARDS_DISABLED`; reads work.
- A project whose root is missing can be listed and read by the dispatcher; its writes are refused with `ROOT_UNAVAILABLE`.
- The dispatcher's 41st creation or start in an hour is refused with `CARD_LIMIT`; its count and a card agent's are independent.
- The dispatcher's folder, and the old one, are never offered or accepted as a Flowly project or bound to a card.
- Start without a provider uses the Dispatcher model setting, else `claude/claude-sonnet-5-5`.
- A corrupt `dispatcher.json` is preserved and treated as empty.
- Transcript entries and note rows interleave by time; note-batch messages appear only as note rows, one per note the dispatcher received. The chat shows no ask, answer or change row (`client/dispatcher-panel-logic.test.ts`).
- The change line counts the cards changed since the mark, without the user's or the dispatcher's own actions; Mark seen hides it until something new changes, including a later event in the same millisecond; a mark ahead of the daemon's clock is clamped; it shows as the Attention tab's Updates section, never in the bell's count.
- A live dispatcher whose `guard` is absent, of an older version or on a provider other than Claude shows the unguarded warning and Replace dispatcher, and gets no board notes (they are held, nothing is sent to it); a started one records the current guard and shows none; an ended one shows none.
