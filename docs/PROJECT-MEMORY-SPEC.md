## 1. Purpose, and whether it is worth doing

### 1.1 Problem

Every card's session starts from zero. Decisions made and pitfalls hit inside a card stay only in that card's conversation and summary. To let the next card know, the only way today is for the user (or an agent the user asks) to write them by hand into `AGENTS.md` or some spec.

This repository does exactly that: `AGENTS.md` is already 17.7 KB (about 5k tokens), with 9 decisions carrying dates or "user-approved / declined", and every session loads it in full. There are also more than 70 specs, with pitfalls scattered through them that matter only for specific topics, for example "the Claude provider does not enforce `outputSchema`, so recap may return an array" (TASK-SUMMARY-SPEC §3) and "the plugin data directory gets registered by Paseo as a native project" (TASK-SUMMARY-SPEC §2). A later card hitting the same topic learns of it only if its agent happens to read that spec.

### 1.2 Judgment: is knowledge accumulation necessary

Necessary, but what is needed is **curation**, not **accumulation**:

- The necessary parts are **collection** and **topic-based recall**:
  - Collection: what is settled in a conversation now depends on a person remembering to write it down, and often gets lost.
  - Recall: knowledge relevant only to some tasks should not occupy every session's context, nor be buried in a spec waiting for someone to read it by luck.
- The unnecessary and even harmful part is a **knowledge base that grows without limit**. The more memory there is, the more outdated and mutually contradicting entries there are, which mislead the agent. Critics of Claude Projects complain precisely that the memory can be neither seen nor edited. So this design:
  - makes every memory take effect only after a human confirms it;
  - caps the number of entries (§3.3);
  - lets a new entry supersede an old one;
  - shows when each entry was last used, to ease cleanup;
  - lets an entry that everyone should follow be moved into `AGENTS.md` with one click and leave injection (§5.4).
- For this repository the benefit is moderate: the user is already used to writing rules into `AGENTS.md` and specs. The benefit is mainly in three places: collection no longer depends on people remembering; topic-specific pitfalls reach the right card; and `AGENTS.md` need not keep growing. For projects with no habit of maintaining `AGENTS.md`, the benefit is larger.

Conclusion: do it, but narrow v1 to "a list of human-confirmed decisions and pitfalls + topic-based injection", with no semantic retrieval and no automatic activation.

## 2. What goes into project memory, and what goes into AGENTS.md

### 2.1 What to store: four questions (2026-10-22, the user asked "what exactly should cross-card shared memory store")

In one sentence: **store what another card's agent would otherwise re-ask you, re-try, or re-hit if it did not know**, and which is not yet written into code, a spec or AGENTS.md.

Ask four questions, each corresponding to a type:

| Question | Type | What is stored |
| --- | --- | --- |
| Will other cards later ask the user the same question again? | `decision` | The trade-off the user settled and the reason, **including rejected options** ("not doing X, because Y") |
| Has a path been tried or investigated that does not work? Is there a general lesson behind a bug that was fixed? | `pitfall` | The symptom, the cause, how to avoid it; and "investigated, no better way, do not investigate again" |
| How does the user want things done in this project, when the repository does not say? | `convention` | The user's working preferences and process, for example write MR descriptions per the template, do not keep watching CI, commit only this card's changes |
| Is there information about people, systems or environments outside the project? | `contact` contacts and external systems | Who reviews, which Jira project, which test environment, the address of an internal service (no secrets) |

**Not stored**:
- This card's progress (the summary);
- Todos and "later" matters: these should become an idea or a card, otherwise they become a "memory" that is never handled;
- What can be read directly from code, git history or docs;
- Rules every task must obey: these go in AGENTS.md (§2.3).

**Actual data from this machine's board** (2026-10-22, read-only scan, 5 projects, 75 cards, 474 summary versions). 35 cards had decision- or finding-type points in their latest summary; classified:

| Point (excerpted from the summary) | Card | Classification | Already elsewhere? |
| --- | --- | --- | --- |
| The settings page froze because two Modals switched in the same frame; changed to open after a 450 ms delay | Add new user onboarding | `pitfall`: any later card that opens and closes two Modals at once will hit it | Only the code fix exists, the general lesson was not written down → **should be recorded** |
| The button sat in the title bar, and on hover the title bar believed the mouse had left and set opacity to 0 | Fix the lane collapse/expand button | `pitfall` | Same → **should be recorded** |
| The latest Paseo source has no more responsive input approach, and the user agreed to keep the status quo | Pad version supports desktop layout | `pitfall` (investigated, do not investigate again) | Not written down → **should be recorded**, otherwise the next card touching the input box will investigate again |
| The user asked to stop watching CI; MR descriptions filled in per the template | Adjust service middleware order (Search System) | `convention` | The Search System root has no AGENTS.md → **should be recorded** |

From this:
- In the **Flowly project**, the user requires "decisions to be written into the matching spec", so most **decisions** already have a home, and the value of memory is mainly in **pitfalls**, especially the two kinds "fixed but the general lesson not written down" and "investigated, dead end".
- In projects like **Search System**, with a shared root and no AGENTS.md under it, **conventions** and **contacts and external systems** have nowhere else to go, so the value of memory is larger.
- This also shows the review should not often produce results: among 35 cards roughly 5–8 entries are worth recording, an average of 0–1 per Done card. The "better none than padding" of §4.2 is set by this ratio.


### 2.2 Position of each store

| Store | What goes in | Who reads it | Lifecycle |
| --- | --- | --- | --- |
| Repository instruction files (`AGENTS.md` / `CLAUDE.md`) | Rules **every task must obey** that evolve with the code: build and test commands, architecture constraints, product invariants, coding standards | Loaded natively and in full by every session, including sessions outside Flowly, CI, teammates | In git, reviewed through PRs, shared across machines |
| spec / docs | The complete behavior, contract and acceptance of one feature | Read when needed | In git |
| **Project memory** (this feature) | Knowledge **relevant to only some tasks**, needing a source and date, or **not suited to the repository**: decisions with reasons, pitfalls hit, conventions, contacts and external systems | Only the relevant entries are injected into a new card session's initial instructions (§6), the rest are looked up on demand with `flowly_recall` | Stored in the local daemon, split by Flowly project, human-confirmed and editable, not in git |
| Card summary / workpad | This card's progress, acceptance criteria and checks | This card | Goes with the card |
| Provider's own memory (such as Claude Code auto-memory) | A single provider's own memory | Only sessions of that provider | Flowly neither reads nor writes it |

Compared with `AGENTS.md`, project memory differs in five places:

1. **On-demand injection**: each entry has a type and tags, only the few relevant to the new card are injected, with a character limit. `AGENTS.md` is injected in full.
2. **Traceable**: each entry records its source card, its proposer (agent, review or human) and confirmation time, and can be clicked back to the source card. A one-line rule in `AGENTS.md` does not show which card set it or why.
3. **A human-confirmed inbox**: agents and the review can only propose candidates, and the human confirms, edits or ignores them in Flowly. Changing `AGENTS.md` requires an agent to edit the repository file directly, followed by a human reviewing the diff.
4. **Not in the repository**: contacts, internal links, personal preferences, and pitfalls tied to one machine are not pushed to a remote.
5. **Cross-repository**: a Flowly project can be a shared directory holding several repositories, or a linked root (PROJECT-PICKER-SPEC). Memory is stored per project and belongs to no single repository's `AGENTS.md`.

Provider-neutral: the same memory takes effect for Claude, Codex and Pi sessions. A provider's own memory cannot do this.

### 2.3 Decision rules

Before an agent proposes a candidate, when the review distills, and when a human reviews, the same set of rules is used, judged in order:

1. Contains a secret, token or password → **goes nowhere** (the daemon rejects it, §4.1).
2. Only about this card's progress or acceptance → card summary or workpad, **not memory**.
3. Can be read directly from code, git history or existing docs → do not record (a line in memory pointing to "see docs/X §n" is allowed as a pointer, but do not copy the content).
4. Every task in this repository must obey it, and it is suitable to be public in the repository → **`AGENTS.md`** (when such a candidate shows up in memory, the review UI offers "move into AGENTS.md", §5.4).
5. Everything else that would change how **another, later card** does its work → **project memory**.

Examples:

| Content | Where | Reason |
| --- | --- | --- |
| "After changing client code, run typecheck and then reload the plugin" | AGENTS.md | Applies to every task |
| "The Claude provider does not enforce outputSchema, recap may be an array, parse tolerantly" | Memory (pitfall, tag `ai-features`) | Only cards that write child-session output parsing need it |
| "The phone does not use expo-image-picker: the user declined on 2026-10-21" | Memory (decision); this repository already wrote it into AGENTS.md, so do not record it again | Rule 3: already documented |
| "Paseo registry submissions go through the issue form + submission label, contact X" | Memory (contact) | Relevant only to release cards; includes a person's name |
| "This card changes the summary to once every 5 turns" | Do not record | Rule 2: this card's progress; and once implemented it can be read from the code |

## 3. Data and storage

### 3.1 File

A separate file `memory.json`, in the same directory as `board.json`, done like `summaries.json` and `digests.json`: serialized writes, a `.bak` backup before writing, atomic replacement; when the content is invalid the file is kept and an error is reported, never reset.

The reason for not putting it in `board.json`: clients often read the board by etag, and the phone decodes on the JS thread (PERFORMANCE-SPEC). 200 entries of 1000 characters each would make every board read heavier, while the board itself does not need the memory text.

```
{ version: 1,
  entries: MemoryEntry[],
  errors:  [{ taskId, at, message }],      // review failures, only the latest one kept per card
  retros:  [{ taskId, at, summaryId?, clueAt? }],   // the summary version and latest clue time used by each card's latest review (§4.2 dedupe)
  recallStats: { [projectId]: { queries, empty } },  // recall count and empty-result count over the last 30 days (§6.4)
  clues:   [{ id, taskId, at, kind: "answer" | "feedback" | "message", ask?, text }] }  // clues collected during work (§4.0)
```

### 3.2 MemoryEntry

```
{ id, projectId,
  kind: "decision" | "convention" | "pitfall" | "contact",
  title     non-empty, ≤120 characters
  body      ≤1000: the content; for a decision write "what was settled + why", for a pitfall "symptom + how to avoid it"
  tags      ≤4, same rules as card tags (CARD-TAGS-SPEC), reuse projectTags where possible
  keywords  ≤12 search words, each ≤40 characters: synonyms, phrasings in both English and Chinese, involved file or module names, used only for recall (§6.2)
  pinned    boolean: always injected (§6.2), at most 5 per project
  status: "candidate" | "active" | "dismissed" | "archived",
  archivedReason?: "retired" | "promoted" | "superseded",
  supersedes?: id            // the active entry a candidate would supersede
  source: { by: "agent" | "retro" | "human",
            taskId?, agentId?,          // the source card and the proposing session
            eventId? }                  // the card event written when an agent proposes, used for idempotency (§4.1)
  revision: number           // incremented independently per entry, manual edits reject stale writes by it
  createdAt, updatedAt, confirmedAt?,
  usedAt?, usedBy?: string[] }   // last used time; the latest 20 distinct cards that used it
```

- State transitions: `candidate → active` (confirm), `candidate ↔ dismissed`, `active ↔ archived`, any state → permanent delete. An entry a human creates is `active` directly.
- `usedAt` / `usedBy`: when an entry is injected into a new session or returned by `flowly_recall`, record the time and the card (deduplicated, at most 20 kept). Best effort, written at most once an hour per entry; values not yet written are lost on plugin reload. Used only for the promotion and cleanup hints of §6.5, and never automatically deletes or archives an active entry.
- After the source card is permanently deleted, `source.taskId` is kept, and the UI shows "From a deleted card".

### 3.3 Limits

These limits are set for human review and the injection budget, not because the file cannot hold more: with 200 active memories a person can still go through them one by one and maintain them, with 2000 they cannot. The capacity of the file itself is in §3.4.


| Item | Limit | When exceeded |
| --- | --- | --- |
| Active per project | 200 | No automatic retirement; on confirm or create, the UI makes the user first archive one of the recommended rarely used entries (§6.5) |
| Candidate per project | 50 | The agent gets `MEMORY_LIMIT`; the review discards extra candidates and records one error |
| Unhandled candidates per card | 5 | `MEMORY_LIMIT` |
| Dismissed + archived per project | 200 | Delete the earliest, written to a `removed/` backup |
| Pinned per project | 5 | Rejected |

### 3.4 Why store in a file and not connect an external memory system (2026-10-21, the user asked: is a file alone too inefficient, does it have a ceiling, should we connect mem0 or the like)

**Efficiency is not a problem.**
- Measured on this machine: `board.json` is 2.7 MB (75 cards, 2880 events), and Python parses it once in about 15 ms; `summaries.json` is 0.5 MB.
- At full capacity memory is 200 entries × ≤1000 characters, at worst about 0.6 MB (counting Chinese at 3 bytes), and in practice mostly within 100 KB.
- Reads are rare: only when creating a session, `get_task`, `recall` and opening the Memory page. The daemon caches the file in memory, and scoring 200 entries takes under a millisecond.
- Writes happen only when a human confirms or edits, an agent proposes a candidate, or the review runs, and each atomic whole-file replacement takes a few milliseconds.
- Even if opened up to tens of thousands of entries, a linear scan would still take milliseconds. The limit of §3.3 is a product choice, not a storage limit.

**The real weakness of file storage is recall quality, not storage**: word matching cannot match synonyms or mixed Chinese and English usage (for example the Chinese word for "summary" and the English "summary"). This is precisely the strength of systems like mem0, which do semantic recall by vector similarity. But connecting them in this plugin costs more than it gains:

| | mem0 / OpenMemory kind | This design's requirement |
| --- | --- | --- |
| Writing | The core selling point is an LLM automatically extracting facts from conversations, automatically adding, merging and deleting | Takes effect only after a human confirms; an agent can only propose candidates, not change them. This is exactly the problem this card is solving (Claude Projects is criticized for "memory that can be neither seen nor edited"), and after connecting it its core function would have to be turned off |
| Dependencies | Needs an embedding model and an LLM API key (OpenAI by default, or local Ollama), and a vector store (Qdrant and so on; OpenMemory also needs Docker + Postgres) | The plugin currently calls models only through Paseo's agent providers, has no API key of its own, and does not require the user to install extra services |
| Where data goes | The cloud version sends content to a third party; the local version also sends text to an embedding service | Memory holds contacts and internal information, which should stay on this machine |
| Consistency | An external store has none of this plugin's revision checks, `removed/` backup, or cascading delete on card deletion and project removal | AGENTS.md: persist in the daemon, serialize writes, atomic replacement, reject stale edits, keep invalid data without resetting |
| Scale | Suited to tens of thousands to millions of entries, with no human review | Tens to two hundred entries per project, each reviewed by a human |

**Conclusion**: v1 uses `memory.json` as the only data source and connects no external system. Recall quality is improved in two steps:

1. **v1: search words**. Each memory carries `keywords` (§3.2), written by the agent or the review when proposing a candidate, and the human can change them. Scoring weights keyword hits (§6.2); a memory that spells out different phrasings such as "summary / summarizer" (including their Chinese equivalents) solves most synonym and Chinese-English mismatches without embeddings.
2. **Later: a replaceable recall layer**. `memoryForTask` / `recall` of `shared/memory.ts` are written as a ranking interface whose input is the entries and a query text and whose output is the ranked IDs. If a semantic index is ever built, it hangs behind this interface only as **derived data**: rebuilt from `memory.json`, deleted and rebuilt when broken, storing nothing that exists only in it. The possible implementations are a local embedding model, an embedding provider the user configures, or mem0 used only as a vector store (with its automatic extraction turned off).

**When to reconsider**: when any project's active memories exceed 150 entries, or more than 30% of `flowly_recall` queries return 0 entries (the daemon only counts, and does not record query content). At that time open a separate card to evaluate, not in this card.

**No conflict with memory MCPs the user installs themselves**: the user can install mem0 / OpenMemory or similar MCPs for Claude or Codex separately; Flowly neither reads nor writes them, the same as a provider's own memory (§2.2).

## 4. Sources

### 4.0 When to summarize, how often, and how (2026-10-22, the user asked)

**Data first** (this machine's flow log, 2026-10-15 to 10-21, read-only): 10–22 moves into Done per day (including moving back in after moving out), 7–18 agent questions, and 35–88 rework bounces from In review.

This sets three principles:
- **The user's own words are the most valuable, but they are not on the board**. Decisions and corrections happen at two moments: the user's answer after an agent question, and the user's feedback after delivery. This text lives only in the session conversation, and the summary keeps only a few compressed lines, where the "why" and the dead ends are often squeezed out. So the **original words must be recorded** during work.
- **Recording original words costs no tokens, distilling does**. Collection is done by rule, without calling a model; distillation is done only once per card.
- **No periodic summarizing by time**. Memory is produced per card, and the material is fullest when the card is done; summarizing by day or by week would mix several cards' material and would also run idle when there is no new material.

So there are three layers:

| When | Frequency | What | Cost |
| --- | --- | --- | --- |
| **During work, the agent itself** | At each delivery, the agent decides | With full context, the agent proposes candidates with `flowly_remember` per the four questions of §2.1 (§4.1) | 0 (the agent is running anyway) |
| **During work, the daemon collects clues** | At the end of each turn (the `agent.turn_ended` hook, non-blocking) | Record the original words by rule, without calling a model (see "Clue collection" below) | 0 |
| **Card moves into Done** | Once per card; when moved out and in again, rerun only if there are new clues or a new summary | Review: hand the clues, summary history and workpad to the Summary model and distill 0–1 candidates (§4.2) | One Haiku call per card, input about 3–4k tokens |
| Periodic | **Not done** | Staleness and frequent use are only hinted by rule (§6.5), with no model call to merge or rewrite | 0 |

By the data above, Flowly makes about 10–20 review calls per day. Approaches considered and not adopted:
- Distill every turn: a hundred or more calls a day, and most turns ("continue", "commit") have nothing worth recording;
- Batch distill weekly: the material waits a week, and the card may already be wrapped up with its session archived;
- Read the summary only at Done: the summary is a compressed result and drops the "why".

**Clue collection** (rules, `server/memory.ts`). At `agent.turn_ended`, take the `user_message` at the start of this turn's timeline, pass it through the filters below, and record one clue. Every message the user wrote themselves is recorded, with a type marked by scenario, which the review uses for weighting:

- `answer`: before this turn started, this session's last report on this card was `kind=question`, with no new report after it → also record the question (`ask`, taken from that report's note);
- `answer`: this turn's timeline has an answer the user gave through a native question tool → one clue per question, with `ask` being the question and `text` the answer. Even a short answer is recorded (the question gives the context); only empty answers and secrets are filtered. The format was checked on 2026-10-22 against this machine's real timeline and the Paseo source (`questionAnswers` in `shared/memory.ts`):
  - **Claude `AskUserQuestion`**: a completed `tool_call` in the same turn. The question is in `detail.input.questions[].question`, and the answer is in `detail.output.output`, shaped like `"question"="answer"`. The outer sentence varies with the Claude Code version (both `Your questions have been answered: …` and `The user answered: …` were observed), so only the quoted pairs are parsed.
  - **Codex `request_user_input` (synchronous)**: a completed `tool_call` in the same turn, `metadata.questions[]` (`id`, `question`) plus `metadata.answers` (an answer array by question id, multiple choices joined with ", ").
  - **Codex `request_user_input_async` (asynchronous)**: this turn only issues the question, and the answer is later sent back to Codex as a user message, beginning with `Answers to your questions:`, with one paragraph of "question line + answer line" per question. The answers are parsed from this message; if it is the first message of a turn, it is not recorded again as a `message`. The async tool call itself is not read: the rendered text structure is the same whether answered or unanswered, and when dismissed it ends with `Dismissed`.
  - Dismissed, failed or interrupted questions are not recorded. The clue id of one question is made of the session and the call id, so being fed into the hook repeatedly in the same turn still records it only once.
  - Pi's question tool has no record on this machine to check against, so it is not handled for now.
- `feedback`: the card is in In review when this turn starts, that is, a reply after delivery;
- `message`: the rest of the messages the user wrote themselves, including the card's first instruction.

From 2026-10-22 every message the user wrote themselves is recorded, no longer only answers and feedback. In the walkthrough (§2.4), 3 of the 10 entries worth recording appear only in the user's ordinary messages (commit identity, version upper bound, preference for the simple approach), and recording only answers and feedback would miss them.

Filters:
- Fewer than 15 characters are not recorded, for example "continue", "ok", "commit and push" (the Chinese equivalents of these short replies are likewise dropped);
- A text exactly identical to some next move or idea instruction is not recorded: that is a suggestion the user tapped, not words the user wrote;
- A message that hits the secret rule (§4.1 `MEMORY_SECRET`) is dropped whole. The walkthrough had a message with an npm token pasted in;
- At most 600 characters each; at most 30 per card, and when exceeded keep the first (the card's original requirement) and drop the earliest of the rest.

Storage:
- Clues are used only as input to the review, are not injected, and are not shown on the Memory page;
- After a successful review keep them 30 days (convenient for a manual rerun), then delete;
- Deleted together on card deletion and project removal, with a backup written;
- Not collected when memory is off (§9).


### 4.1 Agent tool `flowly_remember`

Input (strict):

```
{ expectedRevision, request,              // same as other write tools, from flowly_get_task
  kind: "decision"|"convention"|"pitfall"|"contact",
  title, body,
  tags?: string[] = [],
  keywords?: string[] = [],              // search words for recall (§3.2)
  supersedes?: string }                   // the ID of the active entry to supersede
```

- Identity, signature, expiry, revision, archived and finished checks are all the same as `flowly_propose_idea`; it changes neither the card status nor the task revision.
- Write order (decided during implementation, 2026-10-22):
  1. First do the memory validation outside the board (off, duplicate, over limit, secret, supersedes); a rejected call leaves no receipt;
  2. Then go through the same board transaction as other write tools: the receipt goes in `board.agentReceipts`, and the card records a `memory_proposed` event;
  3. Finally write `memory.json`, idempotent by that event's id (`source.eventId`).

  The board transaction callback is synchronous and cannot wait inside it for `memory.json` to finish writing, so the order is the opposite of the design draft. When step 3 is lost (for example the daemon happens to restart), replaying with the same request gets the original receipt and backfills that candidate by eventId, without producing an extra one. On replay, the same parameters return the original receipt and the original `memoryId`, and different parameters give `REQUEST_REUSED`.
- Event: the source card records `memory_proposed` (agent, note=title).
- Errors:
  - `MEMORY_DISABLED`: the project turned memory off (§9).
  - `MEMORY_DUPLICATE`: this project already has a candidate or active entry with the same title (trimmed, case-insensitive); the message carries the existing ID and suggests using `supersedes` to supersede it.
  - `MEMORY_LIMIT`: §3.3.
  - `MEMORY_SECRET`: the title or body hits the secret rule. It reuses the redaction rules of Workflow insights (`shared/workflow-insights.ts`); on a hit it rejects, and does not replace and save.
  - `INVALID_INPUT`: `supersedes` is not an active entry of this project.
- Output: `toolResultSchema`, with one more `memoryId`.
- The CLI adds `remember --request-file … --kind … --title … --body … [--tags a,b] [--supersedes <id>]`; the HTTP `/api` `action` adds `"remember"`.
- `scope: "project" | "umbrella"` (optional, default `project`): `umbrella` writes a feed entry of the card's umbrella instead of a project note and never touches `memory.json`; see UMBRELLA-SPEC §6 (and §4.1 for its errors).

### 4.2 Finished-card review (distill candidates at Done)

It reuses the way the summarizer child session runs (TASK-SUMMARY-SPEC §2, PROJECT-INSIGHTS-SPEC §7).

- **Trigger**: the card enters Done (anyone moving it counts), project memory is on (§9), and the review setting is on. Cancelled does not trigger: a cancelled card mostly has no conclusion to settle, and it can be triggered manually if needed.
- **Wait**: after entering Done wait 30 seconds so the last turn's summary is written; if that card's summarizer is still running, wait at most 120 more seconds.
- **Skip**:
  - The card has no summary, and no workpad confusion points or progress records → no material, skip;
  - Since the last review there is neither a new summary (`retros[].summaryId`) nor new clues (`retros[].clueAt`) → skip, to avoid rerunning when a card moves back and forth between Done and other lanes.
- **Where it runs**: the project's "Flowly background" workspace ([BACKGROUND-WORKSPACE-SPEC](BACKGROUND-WORKSPACE-SPEC.md): restore the archived one for reuse before use, create a new one only if none exists, and archive after the last background run ends). The card's own workspace is not used, because auto wrap-up may archive it right after (MULTITASK-SPEC), and the "project root workspace" cannot be found by directory either: under single-root every card's workspace directory is the project root, and an old rule once made all reviews land in the same card (fixed 2026-10-23). Labels: `flowly=summarizer`, `flowly-project=<id>`, `flowly-task=<taskId>`; the model is the Summary model (Auto resolves the same); `waitForFinish(120000)`, **hard delete** in `finally` (`daemonRemoveAgent` in `server/summarizer-remove.ts`, the local `DaemonClient.deleteAgent`, under the same AGENTS.md exception as the card summarizer, approved by the user 2026-10-22; only the id just created this time is deleted), and if the delete fails fall back to archiving and log it. During the tens of seconds it runs it is briefly visible in the background workspace, and when it ends neither the session nor the workspace is left in the sidebar. At most one runs per project at a time, the rest queue.
- **Input** (≤10000 characters):
  - Project name; card title, type, tags, description (≤2000);
  - This card's clues (§4.0), in time order, total length not over 5000 characters, preferring `answer` when exceeded;
  - Summary: the latest version's target / recap / next, plus the **recap lines that appeared in all historical versions** (deduplicated). Early findings are often squeezed out of later versions;
  - The workpad's confusion points, and failed checks (including those that later passed, since "failed first then passed" is often a pitfall);
  - This card's latest 10 blocker / question / result progress entries (each ≤500);
  - The IDs, types and titles of this project's active memories (≤100 entries), to avoid duplicates and to propose supersession where needed;
  - This project's candidates still awaiting review (type, title), not to be repeated;
  - This project's candidates the user ignored (latest 30, type, title), telling the model what this project does not want;
  - The project root's `AGENTS.md` and `CLAUDE.md` (counted once if identical, skipped if missing), placed after the card material, with a separate limit of 20000 characters that does not squeeze the card material's 10000. What is read is the file on disk at review time, so a rule this card itself just wrote into an instruction file will not be proposed again as a memory.
- **Output schema**: `{ candidates: [{ kind, title, body, tags, keywords, evidence, reuse, supersedes? }] }`, **0–1 entries** (`RETRO_MAX_CANDIDATES`). `reuse` names a later card that works on **a different feature** and would go wrong from not knowing this entry (such as "any card that opens a dialog from within a dialog"); a candidate with an empty `reuse` is discarded before the cap is applied and is not stored. `evidence` (≤300 characters) quotes the original words or recap line relied on, and the review UI shows it under the candidate as a muted quote so a human can quickly judge whether it is true; candidates an agent proposes with `flowly_remember` do not have this field. The prompt's key points:
  - The default is empty; propose at most one, and it must pass the generality test: a later card working on **a different feature or module** can be named that needs it. If only cards of the same feature, the same file, the same bug or the same design can be named, do not propose; that knowledge stays in this card's code and summary. How this card's own feature is designed and implemented, even if the user decided it, does not count as project memory;
  - Judge the type by the four questions of §2.1;
  - Do not propose the same kind as an ignored candidate, nor one already awaiting review; an existing entry about the same problem counts as existing even if worded differently or with more detail;
  - Use no tools;
  - A fixed bug is proposed only when there is a general lesson, writing the lesson and not the fix itself; a conclusion of "investigated, dead end" should be proposed;
  - Do not propose what is not decided or is "later" (that is an idea or a card);
  - Do not propose this card's progress, nor what the repository instruction files already say;
  - Judge by §2.3;
  - Better none than padding; return an empty array if there is none;
  - The language is outputLanguage (AI-LANGUAGE-SPEC).

  Parsing tolerance is the same as TASK-SUMMARY-SPEC §3.
- **Result**:
  - Each candidate's `source.by` is recorded as `"retro"`, with the source card; those that fail the §4.1 validation are discarded: duplicates are discarded silently (the model saw the existing titles, so a duplicate is not a failure), and over-limit and secret hits record an error;
  - The source card records a `memory_proposed` event (actor system);
  - On failure or timeout record it in `errors`, with no automatic retry.
- **Manual**: the sidebar of a Done or Cancelled card has a **Find memories** button that ignores the "skip" conditions and runs once immediately.

## 5. Human confirmation and editing

### 5.1 RPC

| Method | Input | Behavior |
| --- | --- | --- |
| `memory.read` | `{ projectId, etag? }` | `{ etag, value?: { entries, errors, running: taskId[] } }`; read only while the Memory page or the memory section of the card sidebar is visible |
| `memory.counts` | `{ etag? }` | `{ etag, value?: { [projectId]: candidateCount } }`: for the chip in the overview bar, read at the same frequency as the other `*.read-changed` reads |
| `memory.create` | `{ projectId, kind, title, body, tags, pinned }` | Created by a human, takes effect directly |
| `memory.update` | `{ id, revision, kind?, title?, body?, tags?, pinned? }` | Edit a candidate or active entry |
| `memory.confirm` | `{ id, revision, edits? }` | candidate → active; edits can come along; when there is a `supersedes`, the old entry is archived (`superseded`) in the same write |
| `memory.dismiss` / `memory.restore` | `{ id, revision }` | candidate ↔ dismissed; archived → active |
| `memory.archive` | `{ id, revision, reason: "retired" \| "promoted" }` | active → archived |
| `memory.delete` | `{ id, revision }` | Permanent delete, written to `removed/memory-<id>-<time>.json` |
| `memory.retro` | `{ taskId }` | Manual review (§4.2), returns `{ queued: true }` |

- Every write checks `revision`. On a mismatch it reports `MEMORY_CONFLICT`: "This memory changed elsewhere. Reload to see the latest.", and changes nothing. This is the "reject stale edits": when a human and an agent, or two windows, edit at the same time, the later one is rejected and is not silently overwritten.
- Read-only when the project is archived.

### 5.2 Semantics of confirmation

Confirmation is a human action: from then on this entry enters injection. A candidate an agent wrote may be inaccurate, so it can be edited before confirming (Edit → Save and confirm). After confirmation, an agent cannot modify or delete any entry, and can only propose a new candidate to supersede an old one.

### 5.3 Relationship between memory and the source card

Memory belongs to the project, not to the card:

- A card being Done, wrapped up or archived does not affect its memories and candidates (same as IDEAS-INBOX-SPEC §2);
- When a card is permanently deleted, its **candidate / dismissed** entries are deleted (written to the card's `removed/` backup), while **active / archived** entries are kept, because they are already human-confirmed project knowledge.

### 5.4 Move into AGENTS.md (promote)

For an entry meeting rule 4 of §2.3, the entry menu offers **Copy as AGENTS.md rule**:

1. Format the entry as a rule (`- <title>: <body>`), copy it to the clipboard, and tell the user which repository's instruction file to paste it into;
2. After the user taps **Done, stop injecting**, the entry is archived (`promoted`) and no longer injected, so the same rule does not appear twice in `AGENTS.md` and in memory.

The plugin does **not** write repository files: which repository to write to, which section, and whether to go through a PR are all the user's decisions. The workspace is shared by several sessions, and the plugin editing files would mix with their changes (see §14 Q1).

## 6. Use: injection, get_task, recall

### 6.1 Initial instructions

`sessionContext()` gains a parameter `memoryLines`, placed after the artifacts lines and before `Project:`:

```
Project memory (confirmed by the user; 4 of 37 shown, flowly_recall finds the others):    ← "all N entries" when everything fits
- [Decision] Summarizer runs in the project root workspace: auto wrap-up may archive the card's own workspace (memory m_3f2a, from "Task summary")
- [Pitfall] Claude ignores outputSchema: accept arrays for recap and "true"/"false" for booleans (memory m_91c0)
…
```

- Appears only when project memory is on and at least one entry is selected.
- One line per entry: `- [Type] title: first 200 characters of the body… (memory <short ID>[, from "<source card title>"])`.
- Appears on a new session and on explicit work instructions; does not appear on an ordinary follow-up (the AGENTS.md constraint).

### 6.2 Selection algorithm (the pure function `memoryForTask` in `shared/memory.ts`)

Budget: at most 8 entries, at most 2400 characters in total after rendering (about 600–800 tokens).

1. Candidate pool: this project's active entries.
2. **A small project gives everything**: when all entries fit the budget after rendering, inject all. Order: pinned first, then by type (decision, convention, pitfall, contact), and within a type by confirmation time from newest to oldest.
3. Otherwise:
   - pinned entries go in first;
   - the rest are scored by relevance, and those scoring ≥2 go in from high to low, ties by confirmation time from newest to oldest, until the budget is used up:
     - +3 for each tag shared with the card;
     - each word shared between the card text (title + first 2000 characters of the description) and the entry text (title + tags + keywords + first 300 characters of the body) gives +1, up to +4. A word hitting keywords gives +2 each, so different phrasings such as "summary / summarizer" can also match. English is split by `[a-z0-9_-]{3,}` with a small stop-word list removed; for Chinese, Japanese and Korean text, take two-character bigrams of consecutive Han characters;
   - an entry whose score is not enough is not forced in: better to inject fewer than to inject irrelevant entries.
4. The header line says "N of M shown", hinting the agent to use `flowly_recall` to look up the other entries.

Known limitation: a new card often has no tags yet when the session is created, and tags are usually applied only after the agent starts work, so the initial instructions rely mainly on word overlap. `flowly_get_task` recomputes by the current tags each time (§6.3), which can fill this gap.

### 6.3 `flowly_get_task`

The context gains:

```
memory: {
  enabled,
  total,                         // number of active entries
  entries: [{ id, kind, title, body, tags, pinned, sourceTaskId?, confirmedAt }],  // reselected by current tags, full body
  candidates: [{ id, title, status }] }   // candidates proposed by this card (latest 20), to avoid duplicates
```

When memory is off it is `{ enabled: false, total: 0, entries: [], candidates: [] }`.

### 6.4 `flowly_recall` (read-only)

`{ query: string ≤200, kind?, limit = 5 (≤10) }` → `{ entries, total }`.

- It uses the scoring of §6.2 with the card text replaced by `query`; when `query` is empty it returns the most recently confirmed entries.
- It requires only identity, no `request`. The CLI adds `recall --query … [--kind …]`; the HTTP `/api` adds a `"recall"` read action.
- `memory.json` records `recallStats: { [projectId]: { queries, empty } }` per project (last 30 days, counts only, not query content), used to judge the "when to reconsider" of §3.4. The bottom of the Memory page shows a muted line "Recall: 42 searches, 5 found nothing (30 days)".

### 6.5 Lifecycle: promotion and retirement (2026-10-21, the user asked "what if memory fills up, how to retire, how to promote")

"Full" has two kinds, handled differently:

| | What is full | Result |
| --- | --- | --- |
| **Injection full** | A new session's budget (8 entries / 2400 characters) cannot hold all relevant entries | No entry is retired. Only pinned and the highest-scoring are injected, and the other entries are still in the store and the agent can find them with `flowly_recall` |
| **Storage full** | This project's active entries reach 200 | No automatic retirement; a human decides which to archive (see "Retirement" below) |

Entries fall into four tiers, with coverage widening upward. Promotion goes up, and retirement leaves injection:

```
                promote ▲
  AGENTS.md     loaded natively and in full by every session (leaves memory: archived · promoted)
      ▲  Copy as AGENTS.md rule
  pinned        injected into every new session, ≤5 entries
      ▲  Pin
  active        injected when relevant, or found by recall
      ▲  Confirm
  candidate     not injected, waiting for a human
                retire ▼
  archived      not injected and not found, history kept, can be Restored
      ▼  the earliest when archived + dismissed exceed 200
  permanently deleted   written to a removed/ backup
```

**Promotion** is suggested from usage data and executed by a human tapping a button:

- **Commonly used**: an active, non-pinned entry used in the last 30 days by ≥5 different cards (`usedBy`) shows "Used by 6 cards" on the entry, with two buttons, **Pin** and **Copy as AGENTS.md rule**.
- **Pinned entries**: a permanent hint line under the entry: "Pinned memories reach every new session, like AGENTS.md. If this is a rule for the code, move it there.". When pinned is full at 5, one must be unpinned before another can be pinned.
- **Move into AGENTS.md**: see §5.4. After the move the entry is archived (`promoted`) and no longer injected, so the same rule does not appear twice.

**Retirement** has three routes, of which only the first is automatic:

1. **Superseded** (automatic): when confirming a candidate with `supersedes`, the old entry is archived (`superseded`) in the same write. This is the only way an agent corrects memory.
2. **Stale** (hint only): an active, non-pinned entry not used for 60 days (counted from the confirmation time if never used) is marked "Stale". The Memory page has a **Clean up · N** filter, where they can be archived one by one, or one can tap **Archive all stale** (with a second confirmation) to archive them all at once.
3. **Storage full** (human's choice):
   - When active reaches 180 entries, a hint appears at the top of the Memory page: "180 of 200 memories. Archive stale ones to keep room.", linking to Clean up;
   - At 200 entries, confirming a candidate or creating an entry opens **Make room**: it lists the 5 longest-unused non-pinned entries, and after one is chosen and archived the original action continues; the user can also cancel, leaving the candidate unchanged. Agents can still propose candidates, which have their own limit and are not rejected because active is full.

**Why active entries are not retired automatically**: they are human-confirmed knowledge, and "unused for a long time" may just mean that module has not been touched recently. Deleting automatically would let the system judge for the human which knowledge is outdated, which is exactly what Claude Projects is criticized for. The only automatic deletion concerns entries that have **already left use**: when archived and dismissed together exceed 200, the earliest are deleted and a backup is written.

## 7. Skill rules (`server/skill-source.ts` and `skills/flowly/SKILL.md`, English)

Add one rule:

- Project memory in your instructions and in `flowly_get_task` `memory` holds decisions, conventions, pitfalls and contacts that the user confirmed on earlier cards. Follow them. If one conflicts with the repository's instruction files or the user's current request, say so and ask; do not pick silently. Use `flowly_recall` when you start on an area that the shown entries do not cover.
- When something would make a different, later card's agent re-ask the user, retry a dead end or hit the same problem, propose it: a decision the user made, including a rejected option and why (decision); a dead end or a general lesson behind a bug you fixed, not the fix itself (pitfall); how the user wants work done in this project that the repository does not say (convention); people, external systems and environments (contact). Propose it with `flowly_remember`. Only what holds beyond this card: if every later card that would need it works on the same feature, file or bug, leave it to the code and the summary. At most 3 per delivery, usually none. Do not propose this card's progress (that is the summary), open or deferred decisions (those are ideas or cards), what the code, git history or docs already say, or rules the repository's instruction files already contain. If a rule belongs in `AGENTS.md` for every task, still propose it here; the user can move it there. Never include secrets. To correct an entry, propose a new one with `supersedes`; you cannot edit or delete entries.

The delivery-time reminder (NEXT-MOVES-SPEC §9) carries no memory reminder: most cards have nothing worth recording, a reminder would only induce padding, and the review already acts as the backstop.

## 12. Not doing (v1)

- Vector or semantic retrieval, connecting an external memory system (reasons and when to reconsider are in §3.4); cross-project memory; version history of memory (only the current version and the supersession chain are kept).
- Automatic confirmation or automatic deletion; automatic archiving by "unused for a long time".
- The plugin writing repository files (including mirroring into the repository or writing `AGENTS.md`, see §5.4, §14 Q1); reading or writing a provider's own memory.
- Attaching memory to an ordinary follow-up; distilling candidates after every turn.
- Showing a detail of "which sessions this memory was injected into"; v1 records only `usedAt`.

## 13. Risks

- **Outdated memory misleads the agent**: mitigated by human confirmation, the supersession chain, the "Not used / Used Nd ago" hints, and the skill's "ask on conflict", but it cannot be eliminated, and a human needs to glance at it periodically.
- **Review burden**: one more inbox. Mitigation: the review gives at most 1 entry and it must pass the generality test, ignored candidates are handed to the next review as counterexamples, the prompt defaults to returning 0 entries, at most 5 unhandled candidates per card, and no delivery reminder is added.
- **Word-overlap recall is coarse**: Chinese bigrams can mismatch, and a new card with no tags misses matches. Mitigation: a small project gives everything, `flowly_recall`, and get_task reselects by current tags.
- **Context overhead**: at most about 800 tokens per new session; small compared with the 5k of `AGENTS.md`. Once an entry is moved into AGENTS.md, injection stops, so it is not counted twice.
