# Project constraints

## Working relationship

- Act as a colleague, not a subordinate. Before acting on a task or requirement, judge whether it is sound: does it make sense, does it conflict with the product invariants, the specs, earlier user decisions, or itself, and is there a simpler or safer way to the same goal.
- The user can be wrong. When a request contains a clear error, a contradiction with an earlier decision, or a trade-off the user seems to have missed, say so directly and plainly. Do not soften it, hedge it, or bury it after the work. Back the objection with evidence (file, spec section, invariant, concrete failure scenario) and give a recommendation.
- Raise the objection before implementing. If the problem is fundamental (breaks an invariant, loses data, contradicts an accepted decision), stop and get the user's call. If it is minor, state it, proceed with the better option, and say what you changed and why.
- Once the user has heard the objection and still decides otherwise, follow the decision and record it in the relevant spec. Do not re-argue it, and do not silently implement your own preference instead.
- Disagreement is about the work, not deference: do not agree just to please, and do not invent objections to look critical.

## Required reading and delivery order

- Before changing code, read the spec of the area you change (find it in `docs/SPEC-OUTLINE.md`) and the `docs/PROGRESS.md` entries for that area. Search these large files instead of reading them whole.
- The user's later single-root decision supersedes multi-repo product behavior. Read `docs/SINGLE-ROOT-SPEC.md` before modifying project, task, workspace or tool behavior.
- Write or update the spec before implementing a feature: behavior, errors, data contracts and acceptance criteria. A spec holds the contract only; progress, review rounds and history go to `docs/PROGRESS.md` or `docs/verification/`. Keep it in sync with changes. Routine implementation choices within the accepted scope do not require another approval.
- Record completed, failed, and unrun checks separately. A plugin reporting `running` alone does not prove UI or agent behavior.

## Product invariants

- One Kanban project corresponds to one native Paseo project root. New projects and cards use that root only. Users can place multiple repositories under a common directory and register that directory as the native project, or let the plugin create a linked root (a new directory under its data folder with one symlink per chosen repository, `docs/PROJECT-PICKER-SPEC.md`). There is no card repo selector; removing a link deletes only the symlink, never the target.
- Existing multi-repo project/card records are read-only legacy scope data. Preserve their workspace links, scope, activities and receipts; never move directories or reparent native resources implicitly.
- One card corresponds to one workspace; a workspace cannot be bound to two cards. Card edits do not create additional workspaces. A user-confirmed switch (`docs/WORKSPACE-SWITCH-SPEC.md`) moves the card to a new workspace; the earlier one is archived and kept as read-only history.
- A card's sessions are the sessions in its workspace. Multiple sessions are supported; users choose which session receives instructions.
- A card's ordinary follow-up sends exactly the user's text after fresh task/workspace/session authorization. Give task context at session creation or through the explicit Kanban work-instructions action; do not prepend a task header to every message.
- Card business status and session execution status are independent. A turn ending never automatically completes the card.
- Automatic assignment, multi-agent handoffs, role orchestration, cross-host scheduling, and PR automation are outside v1.
- Exception, user-approved 2026-10-27: with a project's *Auto review* on, an agent delivery to In review starts an automatic review. Flowly may run the project's configured check commands, create a temporary review session in the card's workspace (hard-deleted when done, like the summarizer), and, when the review fails, move the card back to the work stage it was delivered from and send a marked rework message to the delivering session, up to the project's rework limit; past the limit the card goes to Blocked. On for new projects, off for existing ones until the user turns it on (user decision 2026-10-28); a pass never moves a card to Done. See `docs/AUTO-REVIEW-SPEC.md` and `docs/GUARDRAILS-SPEC.md`.
- Archiving plugin records preserves history and does not implicitly archive/delete Paseo resources or directories.
- Exception, explicit only: the user-confirmed **Remove** of a project deletes it and its cards from plugin data (after writing a backup to `removed/`). Only when the user also chooses *Also remove from Paseo*, and no session in its workspaces is running, the native Paseo project is removed too (`paseo project delete`, which keeps every folder, worktree and branch on disk). See `docs/PROJECT-REMOVE-SPEC.md`.
- Exception, explicit only: the user-confirmed **Delete permanently** of a card (any lane) deletes that card, its events, receipts and summaries from plugin data (after writing a backup to `removed/`). Only when the user chooses *Archive* in that dialog, or has *Auto archive on delete* on and the wrap-up preflight is clean, its sessions and its own workspace are archived first (running sessions block; warnings are shown). See `docs/TASK-DELETE-SPEC.md`.
- Exception, explicit only: the user-confirmed **Wrap up** of a Done/Cancelled card may archive that card's sessions, and its workspace only when it is a worktree (Paseo may then remove the worktree directory). It runs after a preflight (running sessions block; uncommitted/local-only commits require explicit acknowledgement) and archives the card last. See `docs/MULTITASK-SPEC.md`.
- Exception, explicit only: **Switch to worktree** copies the main checkout's uncommitted changes into a new worktree for the card and archives the card's previous workspace (only its sessions when the card does not own it); the main checkout is not changed. **Release from main** (user-confirmed) removes exactly the diff the card's worktree holds from the main checkout's working tree, and from its index where those lines are staged, after checking that it applies exactly; a backup patch allows undo. **Switch to local** with *Copy* (user-chosen) applies the worktree's uncommitted changes to the main checkout's working tree only, after checking per file that they apply cleanly (files already there are skipped, any conflict refuses the copy); with *Overwrite* (user-chosen) the worktree's version also replaces each conflicting file after the main checkout's version is saved to the handoff folder; a patch of the changes is saved first. **`flowly_integrate`** (agent, only on the user's request) applies the card's branch to the main checkout's index and working tree and moves the main branch with a compare-and-swap, refusing when it does not apply cleanly. None of them stash, reset, check out or merge in the main checkout. See `docs/WORKSPACE-SWITCH-SPEC.md`.
- Exception, user-requested: moving a card into Done/Cancelled asks whether to wrap it up (archive its sessions and its own workspace; the card stays). With the user's *Auto wrap up* setting on, the daemon does it without asking, only when the wrap-up preflight has no blockers and no warnings; otherwise it records a skip reason. ## Architecture and compatibility

- Plugin ID is `flowly` (formerly `paseo-ultra-kanban`; `migrateLegacyPluginData` copies the old plugin-data/plugin-settings dirs once, leaving them intact). Do not overwrite the separately installed `paseo-kanban` plugin.
- Root code is limited to `index.client.tsx` and `index.server.ts`. Other code belongs in `client/`, `server/`, or runtime-neutral `shared/`.
- Use the supplied Paseo SDK for resources and schema-validated RPC for plugin behavior. Never create a second Paseo connection in client UI.
- Client uses React Native primitives, host-provided modules, theme colors, and compact layouts. No HTML, DOM, CSS strings, `localStorage`, or imports of server/Node modules.
- Keep the UI plain: no unnecessary secondary labels or descriptions; let the layout explain. A page, group or row gets no description or detail line that only restates its title or what the control plainly does. Keep text only when it carries what the layout cannot: cost, privacy, side effects or non-obvious consequences, and state. Applies to new and changed UI; when you remove a string, remove it from every catalog too.
- Exception, web only: `client/web-images.ts` may listen for paste/drop on the session composer node and on the first-message fields of New task and New session (`client/image-attach.tsx`), and open the browser file chooser for image attachments (the host provides no picker). Phones get no image picker until the SDK offers one: reaching the host's `expo-image-picker` native module was declined by the user (2026-10-21). Keep it feature-detected, render nothing as HTML, and keep all other client code DOM-free.
- Exception, phones only, user-requested 2026-10-31: `client/host-horizontal-scroll.ts` finds Paseo's `HorizontalScrollContext` through the React fiber of the lane pager's view and registers a sideways offset while the board is past its first lane, so the host's agent-list swipe opens only from the first lane (`docs/UI-UX-SPEC.md` §5, lane swipe). It relies on Paseo internals, not a plugin API: feature-detect everything, never throw, unregister on cover/unmount, and keep the pager usable when the registry is not found.
- Exception, Android only, user-requested 2026-11-01: `client/android-back.ts` finds react-navigation's screen navigation object through the React fiber of the board root (shared walk in `client/host-fiber.ts`) and takes the Back button only while that screen is focused, so Back steps back through Flowly before Paseo closes it (`docs/UI-UX-SPEC.md` §5, Android Back). It relies on Paseo internals, not a plugin API: feature-detect everything, never throw, and leave Back to Paseo when the object is not found.
- Exception, web only, user-approved 2026-10-20: `client/web-composer.ts` may find a session's Paseo message box (`textarea[data-composer-input]`, matched to its session through the React fiber's `agentId` prop) to fill in a suggested next step from the native Next moves card (`docs/NATIVE-SESSION-SPEC.md` §6.4). It relies on Paseo internals, not a plugin API: feature-detect everything, never throw, and fall back to copying when the box cannot be proven to belong to that session.
- Plugin-owned opens/closes, navigation (including sidebar and session preview Back), and drag/drop feedback must use consistent, short, interruptible transitions. Prefer shared React Native Animated opacity/transform primitives; keep pointer tracking and resizing immediate. Host-owned panes/modals/toasts retain host transitions. Honor system Reduce Motion, stop animation/listener work on cleanup, and cover rapid reversal/stale completion without delaying actions or retaining active subscriptions after close. Successful transient operations use native toasts rather than adding layout rows.
- Performance (`docs/PERFORMANCE-SPEC.md`): the phone's JS thread decodes every response (relay E2EE runs in JS), so poll only what is on screen and only as often as it changes. Prefer the shared queries in `client/queries.ts` (etag `*.read-changed` reads, the streamed live agent list, `sessions.tail`) to re-downloading boards, agent lists or projected timelines. Memoize list items and panes that sit under frequently re-rendering parents (`React.memo` with stable callbacks from `useStableCallback` and content-compared derived props). Loops and transitions run on the native driver; never loop an `Animated.sequence` and avoid animating layout props in hot paths. On phones, hide rather than unmount large trees for navigation. Do not remount a focused input for background data.
- Text input: use `TextBox`/`Field` from `client/ui.tsx` (the session composer has its own equivalent), never a bare controlled `TextInput`. On native the input owns its text: never feed typed text back through `value`/`defaultValue` (React Native pushes a changed value into the native view, erasing characters typed meanwhile and breaking IME composition); change the seed and remount only for outside changes. Keep expensive work out of the keystroke path: debounce it (`commitDelay`) or batch reports, and persist drafts asynchronously. Keyboard avoidance for inline inputs uses `client/keyboard.ts` (native-driver transform, cached geometry, Android timing from the host's react-native-keyboard-controller `DeviceEventEmitter` events with focus/blur fallback, Android status-bar coordinate shift). Plugins cannot import Reanimated or keyboard-controller.
- Cold start (`docs/PERFORMANCE-SPEC.md`): the host evaluates the whole unminified client bundle from source at every app launch, so bundle size is start-up time. Client code must not import `shared/i18n-all.ts`, `shared/i18n/*` or other large static data (catalogs are served by the daemon on demand), and plugin load (`contribute`) starts no network work; defer it (the session-chip poll waits 2.5 s). Check the size with the daemon's esbuild options before adding a dependency or a large table.
- Hermes (phones) gives a loop body's `const`/`let` one binding for the whole loop: a closure that runs later (press handler, timer, measure callback, registration callback) must not capture a `for` loop variable. Build it in a function call or `forEach` instead; V8/web does not show the bug.
- Pin SDK/type dependencies to the host version and keep manifest requirements correct for both daemon and client.
- UI text is translated (`docs/I18N-SPEC.md`): wrap every user-visible string in `t()`/`tn()` (English text is the key), mark module-level tables with `msg()` and translate at render, never call `t` at module load, keep compared strings as English identities, and add each new string to all catalogs in `shared/i18n/`. `npm test` fails on missing, stale or placeholder-mismatched entries. Agent-facing text and daemon errors stay English.
- Persist on the daemon. Serialize writes, validate input, use atomic replacement, reject stale edits, and preserve invalid data rather than reset it.
- CLI/MCP clients must use the running plugin service for writes; they must not mutate its data file directly.
- Use subprocess argument arrays, never shell interpolation. Do not expose tokens or unrelated user configuration in logs.

## Onboarding upkeep

- Every user-visible feature added or changed must update the new-user guidance in the same change (`docs/ONBOARDING-SPEC.md`): add or revise the matching welcome-tour copy in `client/onboarding.tsx` (concept map, loop, the Built in / Guardrails / Insights pages with their switches, the More features list on the last page; `docs/ONBOARDING-SETUP-SPEC.md`) when the feature changes how Projects/Cards/Sessions map to Paseo, the basic loop, or a headline capability, and add a one-time tip (`tipIds` in `client/onboarding-logic.ts`, texts in `tipText` in `client/board.tsx`, priority in `nextTip`) when the feature has a moment worth pointing out. If neither is warranted, say so in the delivery note. Keep README highlights, tour copy and tips consistent, add every new string to all catalogs, extend `client/onboarding-logic.test.ts` for new tip rules, and update the spec's tip table.
- A new tip id is not in anyone's stored `tipsSeen`, so it is shown once to every user, including existing ones: that is how new features get announced. Do not add it to a stored list. Existing users were only marked seen for the tip ids that existed at that time.
- When a minor or major release (x.Y.0 or X.0.0) changes something existing users will not run into themselves (a new setting, a switch whose default differs for them, a moved entry point), add that release on top of `client/whats-new.ts` (its user-visible new features, one sentence each, at most 7, optional Open settings / Take the tour button; older releases stay, back to 1.5.0). Existing users see the newest release once after updating and can page back to older ones; new users skip it because the tour covers it (`docs/WHATS-NEW-SPEC.md`). Patch releases (x.y.Z) never add a What's new entry (user decision 2026-10-27).

## Testing and local installation

- Verification is objective because of who checks and against what, not because of the model: the acceptance criteria and checks are written before implementation (spec or the card's workpad); the implementer runs `npm run typecheck` and the relevant tests before every handoff and reports the commands, exit codes and counts; at each milestone (end of a phase, before the PR of a storage/schema/RPC change, before a release) an independent session that did not write the code runs the agreed checks on the exact commit (in a temporary `git worktree` of it) and owns that evidence. The implementer never edits the verifier's evidence and never weakens an assertion without saying so. The user's choice for the independent session is `claude/claude-haiku-5-5` (2026-10-26). Discover actual availability; do not silently substitute a model.
- Keep the process lean. No independent run per increment, no file-hash freeze lists (the commit SHA is the freeze), no per-command evidence files. One short report per verification run: commit, commands, exit codes, pass/fail/unrun counts; raw output only for failures. After a fix, rerun the whole focused suite instead of stitching earlier passes together. A design advisor reviews at most once plus one re-review, and stops when no new High finding appears.
- Launch all delegated/subagent sessions in full access, as explicitly requested by the user. For Codex pass `settings.modeId: "full-access"` at creation; do not rely on changing the mode after a turn has started. Discover the provider's equivalent mode when using another provider. Pass this requirement to test agents for any children they create, and stop leftover test children when the phase closes.
- Testing sessions may read source, run focused checks, and use the installed plugin against dedicated fixture projects/directories. They own test evidence, not implementation files. Tell them they are sharing the codebase and must preserve others' work.
- Start Paseo subagents in your own workspace (`create_agent` with the current session's workspace). Do not create a new workspace or worktree for a subagent, or start one in another workspace, unless the user explicitly allowed it: Flowly's card sidebar lists only the card's own workspace, so such a subagent disappears from it (user decision 2026-10-28). When isolation seems needed (parallel implementers, a branch other than the checked-out one), ask first and say what the user will lose.
- Do not spawn implementation agents without explicit authorization. The test-session request authorizes testing delegation.
- Run typecheck before installing/reloading. Install the local plugin under its own ID; reload it instead of restarting the daemon.
- A daemon that runs a local checkout should have `FLOWLY_TELEMETRY=0` (or `DO_NOT_TRACK=1`) in its environment, so development installs do not send heartbeats (`docs/TELEMETRY-SPEC.md` §6).
- Use isolated temporary directories and explicitly identified fixture resources. Preserve existing plugins, workspaces, sessions, projects, and data.
- Test-created Paseo projects, workspaces, sessions, cards and temporary directories must be cleaned up when the test finishes. Record their IDs/paths before creation; use `try/finally` where practical; verify cleanup in both the native Paseo registry and the plugin board. Never leave fixture projects visible for the user to clean up. Preserve only report/evidence files under `docs/verification/`. ## Git workflow

- Small, low-risk changes (a few lines, a constant, a copy fix, a doc tweak, a focused bug fix) go straight to `main`: commit on `main` and `git push origin main`. The repository owner's admin push bypasses the PR requirement (`enforce_admins` is off). Run `npm run typecheck` and `npm test` on exactly the tree being pushed first, and still commit only this task's changes.
- Complex changes (new features, multi-file refactors, storage/schema or RPC changes, anything that benefits from CI or a CodeRabbit review before it lands, or when the user asks for a PR) use a branch and a pull request: create a branch from the latest `origin/main` (`<type>/<short-slug>`, e.g. `docs/flowly-logo`), commit there, push it, open a pull request with `gh pr create`, and enable auto merge with `gh pr merge --squash --delete-branch --auto` (auto merge is on for the repository). Then bring the local `main` up to date once it has merged. When unsure which kind a change is, ask.
- For a PR, follow it until it is merged; do not stop at opening it. Watch it with `gh pr checks <n> --watch`. Branch protection requires the `CI gate` check and every review conversation resolved, so read CodeRabbit's threads: fix what is valid (push to the same branch), resolve the thread, and wait for the checks to pass again. Never bypass protection with `--admin` without the user's say-so. Report the final state (merged, or what still blocks it).
- Before opening the PR, run `npm run typecheck` and `npm test` on exactly the tree being committed. When the working tree holds other work, check that tree in a temporary `git worktree` of the commit.
- The working tree is shared with other sessions. Commit only the current task's changes, by hunk when a file mixes work. Never stash, reset `--hard`, check out or otherwise overwrite someone else's uncommitted changes. If switching branches would touch their files, build the commit without switching: use a temporary index (`GIT_INDEX_FILE`) or a separate worktree, push it with `git push origin <sha>:refs/heads/<branch>`, and after the merge move the local `main` with `git fetch` and `git reset origin/main` (mixed: HEAD and index only, the working tree stays as it is). That last step assumes the working tree still holds the committed lines; for a card that switched to a worktree and released its changes from the main checkout, use `flowly_integrate` (with `ref: origin/<main>` after a remote merge) instead (`docs/WORKSPACE-SWITCH-SPEC.md` §10.1).

## Releases and registry submissions

- Release in this order: merge the work, bump PR, tag `v<version>`, wait for the Release workflow (rerun its failed jobs if npm had not synced when the integrity check ran), then submit the registry update. Check npm `latest`, the GitHub Release and its assets before reporting success. See `docs/CI-CD.md`.
- A registry submission or update for the Paseo plugin registry (`getpaseo/plugins`) must be created through the **Submit a plugin** issue form (`https://github.com/getpaseo/plugins/issues/new?template=submit-plugin.yml`, in a browser logged in as the repository owner, for example with `aside exec`). The form sets the `submission` label that the intake bot needs. Never create it with `gh issue create` or the API: this account cannot add labels there, so the issue would have no label and intake would ignore it.
- Title: `Update Flowly to v<version>` (or `Flowly` for a first submission). Source: `https://github.com/JasprW/flowly/tree/v<version>`. Tick Orchestration, Workspaces and Utils. The form has only Source and Categories, so put the exact commit, highlights and requests to the reviewer (for example dropping a `listing.media` override) in a comment, and check afterwards that the issue shows the `submission` label.
- A registry record's `listing.*` overrides win over the manifest per field. Say in the comment when a release's `icon` or `media` should replace an override.
